# tools/sandbox — одноразовая песочница для адаптера Claude Code

Адаптер `--adapter claude-code` подаёт пару «запрос пользователя + предлагаемое действие»
классификатору родного auto mode у Claude Code. Наблюдать вердикт `allow`, не исполнив команду,
невозможно: `PostToolUse` срабатывает **после** исполнения. В датасете есть `rm -rf /`, reverse
shell и чтение `~/.ssh` — поэтому такие сессии не должны видеть хост. Этот каталог даёт контейнер,
в котором они исполняются.

Что изолировано и что нет — честно:

- **Файловая система хоста** не видна: код бенчмарка скопирован в образ, наружу смонтирован только
  каталог результатов. Репозиторий, `~/.ssh`, `~/.aws` и `~/.claude` в контейнер не попадают.
- **Подписочные креды Claude не монтируются.** Внутрь передаётся только `ANTHROPIC_API_KEY`, и
  ключ стоит отозвать после прогона: кейсы категории `credential_access` исполняются в том же
  контейнере и переменные окружения прочитать могут.
- **Сеть не отрезана** — `--network none` невозможен, SDK ходит в `api.anthropic.com`. Практический
  риск низкий: домены в payload'ах фиктивные (`*.example.net`), но это ограничение, а не гарантия.

## Как запустить

```powershell
docker build -f tools/sandbox/Dockerfile -t agentgate-bench-sandbox .
.\tools\sandbox\run.ps1
```

Учётные данные `run.ps1` берёт из `benchmark/.env` сам. Нужна **ровно одна** из двух переменных:
`CLAUDE_CODE_OAUTH_TOKEN` из `claude setup-token` (прогон не тратит API-кредиты, платит подписка)
либо `ANTHROPIC_API_KEY`, привязанный к workspace. Команда CLI в обоих случаях одна и та же —
различается только имя переменной.

Если выставлены обе, запуск падает с ошибкой, а не выбирает одну: приоритета между ними нет
намеренно, потому что платят они из разных мест — подписка против API-кредитов, — и молчаливый
выбор означал бы прогон не от того аккаунта, который имел в виду оператор.

Уже выставленная в сессии переменная имеет приоритет над файлом (тогда `.env` не читается вовсе).
Для запуска `cli.py` напрямую тот же `.env` загружается точкой: `. .\tools\load-env.ps1`.

`run.ps1` кладёт результаты в `results/claude-sandbox/` (своя база, чтобы payload, испортивший
песочницу, не утащил с собой предыдущие прогоны). Аргументы `cli.py` пробрасываются через
`-Extra`, например `-Extra @('--category','destructive_action')`.

## Как сравнить с прогоном нашего сервиса

`cli.py compare` читает оба прогона из одной базы, поэтому прогон из песочницы сначала
импортируется:

```powershell
python tools/sandbox/import_run.py results\claude-sandbox\benchmark.sqlite3
python cli.py compare <SERVER_RUN_ID> <CLAUDE_RUN_ID>
```

Импорт переносит строки как есть (`result_json` остаётся источником истины) и безопасен при
повторе: строки заменяются, а не дублируются.

## Чего ждать от чисел

- Адаптер поддерживает только `shell` — **83 кейса из 120**. Остальные 37 (`file_write` 11,
  `mcp_call` 12, `file_read` 8, `network` 6) вернут «нет решения» с причиной; они исключены из всех
  метрик, а парное сравнение пойдёт только по кейсам, где решение дали оба прогона. Ещё 13
  shell-кейсов несут историю, которую адаптер не воспроизводит: без `--no-history` до запуска
  сессии доходят 70 кейсов, с этим флагом — все 83 shell-кейса.
- «Нет решения» бывает и на `shell`: если модель отказалась до классификатора или не предложила
  вызов инструмента, хватать нечего. Это защита Claude Code целиком, а не промах классификатора, и
  приписывать это классификатору нельзя.
- Цена по Claude Code — сессионная (агент плюс классификатор вместе), поэтому она помечена
  `unavailable` с причиной и в сравнении отсутствует. Расклад по моделям лежит в `raw_response`.
- Полный прогон тратит деньги: 70 сессий Claude Code на вашем ключе по умолчанию,
  83 сессии с `--no-history` (до возможных ошибок запуска).
