# Как устроено направление 1 (adapters)

Как оно реализовано сейчас. Историю решений см. `DECISIONS.md`, дельту к ТЗ — `tz-changes.md`.

## Задача

Кодинг-агент спрашивает подтверждение на каждый тулкол, человек жмёт «Run» не глядя. Плюс
результаты тулов (файлы, веб-страницы, вывод команд) попадают в контекст модели как есть,
вместе с prompt-инъекциями.

Адаптер встраивается в цикл агента в двух точках и приводит вердикт гарда в действие
средствами самого харнесса:

```
                тулкол                              результат тула
                   │                                       │
          ┌────────▼─────────┐                    ┌────────▼─────────┐
          │   PreToolUse     │                    │   PostToolUse    │
          │  POST /v1/decide │                    │ POST /v1/inspect │
          │ allow|ask|deny   │                    │ pass|mask|drop   │
          └────────┬─────────┘                    └────────┬─────────┘
                   │                                       │
   allow → выполняется                       pass → как есть
   ask   → нативный промпт харнесса           mask → текст заменён присланным
   deny  → не выполняется, причина уходит     drop → «[gate] result removed: …»
           модели как ошибка тула, ход
           продолжается
```

Гард — не наша зона. Мы делаем адаптеры, патчи, сборку и инсталлер.

## Слои

```
packages/
  core/          вся логика, ноль зависимостей от харнесса
  plugin-v1/     opencode 1.x + Kilo CLI   (сервер + TUI)
  plugin-v2/     opencode 2.0
  plugin-pi/     Pi
  plugin-codex/  Codex CLI
  plugin-dsh/    DeepSeek Harness
  installer/     npx-инсталлер
  mock-guard/    заглушка гарда для тестов и демо
build/           патчи по харнессам + сборка пинованного билда
```

Адаптеры тонкие: переводят события харнесса в вызовы `core` и применяют вердикт. Правила
режимов и политика недоступности живут в одном месте, чтобы не разъезжаться между харнессами.

### core

| Модуль | Отвечает за |
|---|---|
| `protocol.ts` | Типы `DecideRequest`/`DecideResponse`/`Inspect*` — зеркало `contracts/openapi.yaml`. `LIMITS` |
| `client.ts` | HTTP к гарду: таймауты, `Idempotency-Key`, классификация сбоя (`unreachable` / прочее) |
| `mapping.ts` | Имя тула + аргументы харнесса → `tool` (`shell`/`file_read`/`file_write`/`network`/`mcp_call`), `raw`, `args`, provenance |
| `policy.ts` | `resolveOut` / `resolveIn` — единственное место, где режим и вердикт превращаются в действие |
| `mode.ts` | Чтение/запись режима, `cycle()` |
| `cache.ts` | `InspectCache` (по хэшу результата), `VerdictBook` (вердикт по `callID`) |
| `limits.ts` | Обрезка по лимитам контракта; `raw` и `metadata` считаются в **байтах**, не символах |
| `request.ts` | Сборка тела запроса из `MappedAction` + контекста вызова |
| `history.ts` | Журнал ходов сессии: `Turn`, `History`, обрезка `clampHistory` под лимиты сервиса |
| `config.ts` | Конфиг из env и опций плагина |
| `log.ts` | Построчный лог |

## Режимы

`auto` (решает гард) · `ask` (всё через человека) · `allow` (без промптов, но `in`-фильтр
работает) · `off` (плагин молчит).

Хранятся в `~/.config/gate/state.json` — единственный общий канал между серверным плагином и
TUI. Читается с кэшем по mtime, поэтому переключение применяется мгновенно, без перезапуска.
Пишется атомарно (временный файл + rename).

Переключение: **Shift+Tab** циклит `auto → ask → allow` (в `off` только явно, чтобы случайным
нажатием не снять защиту), `/gate <mode>` — во всех харнессах, `openmagi mode <m>` — из CLI и
только при TTY, иначе агент выключил бы себе защиту через `bash`.

В режимах `allow` и `ask` гард по `out` **не опрашивается вообще**: решение принимается локально.

## Что уходит в гард

`out` — тул, нормализованные аргументы, `raw`, cwd, последний запрос человека, provenance,
`call_id`, режим, версия харнесса и флаг `patched`. `in` — текст результата и его происхождение.

### История диалога

Вместе с обоими направлениями уходит `history` — плоский список предыдущих ходов сессии,
**от старых к новым**. У каждого хода есть `role` (`human` / `assistant` / `toolcall` /
`toolresult`) и `author` (`human` / `agent` / `system`), у тульных — ещё `tool` и `call_id`,
которым `toolcall` связывается со своим `toolresult`. Рядом идёт `protocol: 1`; оба поля
опускаются целиком, когда ходов нет.

Зачем: одно действие вне контекста не отличить от того же действия внутри многошаговой атаки,
где каждый шаг по отдельности безобиден. И наоборот — `rm -rf ./dist` сразу после «почисти
сборку» это не то же самое, что та же команда без такой просьбы.

`author` не дублирует `role`: внутри сабагента «человеческую» реплику написала родительская
модель, и без этого поля классификатор принял бы слова агента за намерение пользователя.

Собирается по-разному, потому что харнессы устроены по-разному:

| Харнесс | Откуда ходы |
|---|---|
| opencode 1.x, Kilo | `chat.message` (человек), `messages.transform` (реплики агента), `tool.execute.before`/`after` |
| Pi | `input`, `tool_call`, `tool_result` |
| opencode 2.0 | только тулколы и результаты — хука на сообщения в 2.0 нет |
| dsh | `tools/pre-execute` / `tools/post-execute` |
| Codex | разбор файла транскрипта: каждый хук — отдельный процесс, память между вызовами не живёт |

Обрезка: не больше 200 ходов и 128 КБ, лишнее выбрасывается **ходами целиком** с начала.
Обрезанный ход читается как полный и врал бы классификатору о том, что агент сделал.

Маппинг тулов покрывает разные словари харнессов: `bash`/`shell`/`execute` → `shell`;
`read`/`write`/`edit` с `filePath` либо `path`; `webfetch` → `network`; MCP-тулы
(`<server>_<tool>`) разбираются на сервер и имя; сабагент (`task`) уходит как `mcp_call`.

## Политика при недоступности гарда

Разделены два случая:

- **Ответ пришёл, но плохой** (не-2xx, битый JSON, таймаут) → всегда `ask`. Никогда `allow`.
- **Гард недоступен вообще** → локальная политика `on_unavailable`: `allow` (умолчание,
  fail-open), `ask`, `deny`. `GATE_FAIL_CLOSED=1` — то же, что `on_unavailable: deny`.

Fail-open означает «пусть решает харнесс», а не «пропустить»: адаптер возвращает управление
штатным правилам харнесса. Иначе плагин ослаблял бы защиту по сравнению со своим отсутствием.

> Умолчание fail-open расходится с гарантией сервиса «`allow` по ошибке недостижим».
> Решение владельца продукта — см. `docs/superpowers/service/specs/adapter-contract-gap-analysis.md`.

### opencode 1.x и Kilo

Хук `permission.ask` объявлен в API, но стоковым бинарником **никогда не вызывается**. Патч
оживляет его: в permission-сервис добавляется reviewer, который видит эффективное решение
правил (`allow`/`ask`) и может заменить его на `allow`/`ask`/`deny`. Reviewer хранится в
замыкании слоя; плагинный сервис регистрирует его при инициализации.

Патчи разные: Kilo переписал permission-модуль, и патч opencode на него не ложится. Оба лежат
в `build/patches/<harness>/`, `build.sh` берёт свой. Сборка пинится к точной версии оригинала —
общая SQLite, билд другой версии прогнал бы миграцию схемы.

Без патча работает **fallback**: `deny` через `throw` в `tool.execute.before`, `allow` — ответом
на событие запроса разрешения (промпт мигает), `ask` — только для тулов с baseline `ask`
в конфиге. Не-тульные permission-запросы (`external_directory`, эскалации) в fallback до
адаптера не доходят.

Ошибки тулов — отдельный случай: `tool.execute.after` на упавшем туле не стреляет, поэтому
текст ошибки фильтруется вторым слоем, в `experimental.chat.messages.transform`.

Kilo зеркалит весь env-неймспейс под `KILO_*` и не понимает `OPENCODE_*`.

### opencode 2.0

Плагин грузится только из npm-реестра, кэш версионный, поэтому спек в конфиге версионный.
Permission-домена в API нет — `ask` деградирует в блокировку. Бандл самодостаточный.

### Codex CLI

Хуки штатные, но грузятся только из установленного плагина: свободный `hooks.json` и `-c hooks.*`
игнорируются. Плагин Codex копирует к себе в кеш, поэтому `core` вендорится внутрь
(`sync-core.sh`). Хук не запускается без однократного подтверждения доверия в TUI.

В 0.146 реализована не вся собственная схема: работает `deny`, а `allow`/`ask`/`updatedInput`
в PreToolUse и подмена вывода в PostToolUse отклоняются рантаймом. Отсюда три скрипта:
`pre` — hard-deny, `perm` (PermissionRequest) — авто-одобрение и HITL, `post` — `block`
вместо подмены текста.

### DeepSeek Harness

Самая прямая интеграция: `tools/pre-execute` принимает ровно `{allow|deny|ask}`,
`tools/post-execute` — `{accept,content}|{block,feedback}`. Ставится записью `insert`
в `cordis.patch.yml` профиля.

## Инсталлер

`openmagi install [--guard-url URL] [--token T] [--only …] [--yes]` (запуск из репозитория:
`node packages/installer/bin/openmagi.js`), плюс `status`,
`doctor`, `mode <m>`, `uninstall`.

Детектит бинарники и конфиг-каталоги, выбирает режим установки (`patched` / `fallback` / `v2` /
`pi`), правит JSONC **с сохранением комментариев**, делает `.bak` и пишет sidecar-запись, чтобы
`uninstall` снял ровно своё. Ключи конфига только добавляются — существующие не перезаписываются.

Для патченных билдов ставит обёртку `~/.local/bin/<h>-gate`: она поднимает патченный бинарник
с плагином через `*_CONFIG_CONTENT` и отключает автообновление. Оригинал не трогается.

Билды берутся из `build/manifest.json` по точному совпадению `(харнесс, версия, платформа)`.
Манифест машинно-зависимый и не коммитится; если билда нет — установка честно уходит в fallback
с предупреждением.

Все шесть покрыты инсталлером.

## Проверка

Автотесты — `npm test` из `adapters/`: 106 тестов на встроенном `node --test`, без сети наружу;
каждый поднимает свой эфемерный `mock-guard`.

Живые прогоны — на моках: `mock-guard` (гард на регулярках, форма ответов как у настоящего
сервиса) и `recon/mock-llm.mjs` (скриптованная OpenAI-совместимая модель). Шаги — `RUNBOOK.md`.

Что патч действительно работает, проверяется A/B: плагин кладёт в каждый запрос флаг
`metadata.patched`, и в ленте решений гарда на стоковом бинарнике он всегда `false`,
на патченном — `true`.

## Стек

TypeScript, исполняется нативно Node ≥ 22.6 и Bun — без сборки. Тесты — встроенный `node --test`.
Сборка нужна только для публикации бандлов (bun). Платформа — `darwin-arm64`.

## Политика: детерминированные правила

Ступень 1 гарда работает без модели, а что она считает заведомо безопасным,
заведомо запрещённым или поводом спросить — это политика, и её должно быть видно.
Поэтому она лежит одним файлом: `~/.config/gate/rules.json`, три группы
`allow` / `ask` / `deny`, и уходит **вместе с каждым решением** в поле `rules`.

Один файл на все харнессы сразу. Политика, которая различается от агента к
агенту, — это политика, о которой невозможно рассуждать.

Инсталлер пишет файл один раз, выбором из трёх уровней (`--level low|medium|high`),
и **никогда не перезаписывает** уже существующий: отредактированная руками
политика переживает переустановку. Читается с кэшем по mtime — правка применяется
к следующему решению, перезапускать агента не надо.

Оговорка по контракту: поля `rules` в `contracts/openapi.yaml` пока нет, оно
согласовано как добавление. Сервис, который его не знает, просто игнорирует —
проверено на развёрнутом стенде, ответы штатные. До того как ступень 1 научится
его читать, политику задаёт профиль на стороне сервиса.

## Установка гарда

`openmagi install` умеет два пути:

- **подключиться к уже поднятому** — `--guard-url` и `--token`;
- **поднять свой** — `--start-guard`, тогда нужны `--llm-url`, `--llm-model`,
  `--llm-key` для ступени 2. Инсталлер генерирует токен, запускает
  `docker compose up -d --build` в `service/` и ждёт, пока `/healthz` ответит.
  Без LLM-ключа ступень 1 работает, а ступень 2 честно падает в `ask`.
