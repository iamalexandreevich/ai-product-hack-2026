## 1. Target user

### Primary user

**[Р]** Основной пользователь — **разработчик, который уже работает с кодинг-агентом в CLI или IDE и уже столкнулся с выбором между подтверждением каждого шага и полным отключением проверок.**

Уточнение, которое команда считает существенным для приоритизации:

**[Р]** В качестве первичного сегмента выбран **разработчик, использующий хотя бы один открытый кодинг-агент** (Kilo Code, OpenCode, Cline/Roo, OpenHands) — один или в небольшой команде.

**Контекст использования** — **[Ф]** из `01_hackathon_case.md`: агент пишет код, ставит зависимости, запускает тесты, нередко сам разворачивает приложение; человек валидирует результат «на вайбе». Продуктивность резко растёт именно тогда, когда агенту дают действовать без подтверждения каждого шага.

**Почему проблема релевантна именно этому сегменту:**

- **[Ф]** У закрытых вендоров auto mode уже есть: Claude Code (по умолчанию с 14 августа 2026), Codex Auto-review, Cursor Run Modes. В открытых харнессах сопоставимого движка нет: в Kilo Code auto mode только проектируется (issue #9138), в Kiro открыт запрос. Источник — кейс хакатона и `03_competitor_research_summary.md` §1.
- **[Ф]** Следствие: у пользователя открытого агента выбор сегодня бинарный — approval fatigue или `--dangerously-skip-permissions`. Это прямая формулировка кейса.
- **[Ф]** Для пользователей open-source-моделей риск выше: по исследованию TRAP, приведённому в кейсе, доля успешных инъекций — 13 % для GPT-5 и 43 % для DeepSeek-R1. Встроенной устойчивости модели может не хватать.

**[П]** Мы считаем, что этот сегмент сегодня чаще всего **просто отключает защиту** — то же зафиксировано как Gap 3 в конкурентном анализе (confidence Medium). Опрос это **не подтверждает и не опровергает**: вопроса «отключали ли вы проверки» в анкете не было.

**[Ф] Что опрос про сегмент всё-таки говорит.** Из 28 респондентов 20 имеют опыт автономного режима, 13 из них запускают его каждый день или несколько раз в день. Инструменты: Claude Code — 18 из 20, OpenAI Codex — 11, Cursor Agent — 5; несколькими агентами одновременно пользуются 14 из 20. Восемь человек режим не используют, и безопасность объясняет меньше половины отказов: недоверие — 3, не знают о возможности — 2, не видят необходимости — 2, не дошли руки — 1 (`09_user_research/README.md`).

**[И]** Приоритет интеграций, который из этого следует для пилота, — Claude Code, затем Codex и Cursor. Это вывод о доступной аудитории тестирования, а не о рыночных долях и не о простоте интеграции. Он совпадает с тем, что бенчмарком измерена именно интеграция с Claude Code.

### Secondary users

**[Г]** **Команда, использующая несколько разных харнессов.** Обоснование — **[Ф]**: политика безопасности сегодня расползается по форматам (`settings.json` у Claude Code, `config.toml` у Codex, `permissions.json` у Cursor, правила `{permission, pattern, action}` у Kilo), её нельзя проревьюить целиком, и она теряется при смене агента (`why-agentgate.md` §2, §7). Ценность единой политики для такой команды — гипотеза, не проверенная ни на одном пользователе.

**[Г]** **Организация с требованиями к периметру данных и аудиту** (on-prem, запрет на отправку кода и запросов пользователя внешнему вендору). Обоснование — **[Ф]**: в закрытых auto mode классификатор является моделью вендора, и каждое действие вместе с запросом пользователя уходит к вендору; в OPENMAGI провайдер ступени 2 задаётся конфигурацией (OpenAI-совместимый API, вплоть до локальной модели). Технически это уже так (`profiles/schema.py: ModelsConfig`), но что этот сегмент готов ставить **отдельный сервис**, а не плагин, — **[?]** не проверено (прямо назван как открытый вопрос в Gap 3).

**[?]** Сегмент «enterprise / платящий заказчик» в проекте не исследован: данных о спросе, готовности платить и объёме рынка в наших материалах нет — конкурентный анализ прямо запрещает такие утверждения («Любые заявления о доле рынка, спросе или готовности платить — в исследованиях данных нет»).

## 2. User problem

### Формулировка

**Разработчик не может одновременно получить производительность автономного агента и уверенность, что агент не сделает необратимого действия, — потому что единственный доступный ему регулятор (подтверждать / не подтверждать) регулирует не риск, а объём его собственной работы.**

### Конфликт, который стоит за этим

Проблема — не «AI-агенты небезопасны». Проблема в том, что три вещи связаны так, что улучшение одной ухудшает другую:

1. **Автономность даёт продуктивность.** **[Ф]** Кейс: «Продуктивность такого режима резко возрастает, когда агенту дают автономию». Именно ради этого пользователь включает bypass.
2. **Человеческое подтверждение — плохой детектор, а не хороший.** **[Ф]** Слепое исследование Anthropic (n = 1 053, приведено в `03_competitor_research_summary.md` §2): люди одобряют 93 % всех промптов; явно опасную подменённую команду блокируют лишь в 13,6 % случаев; catch rate падает с ~17 % в начале сессии до ~5 % после 50 промптов. Auto mode в том же тесте блокировал 89 %. То есть **friction, которую платит пользователь, не покупает ему безопасность** — она покупает ощущение контроля, деградирующее по ходу сессии.
3. **Цена ошибки в автономном режиме — необратимая.** **[Ф]** Канонический пример из конкурентного анализа — инцидент Replit Agent (удаление production-базы во время code freeze, июль 2025). Кейс перечисляет тот же класс: установка вредоносного npm-пакета, раскрытие секретов по инструкции из заражённого навыка, удаление промышленной БД.

Отсюда — форма конфликта, а не просто перечисление:

- Если поднять долю подтверждений, растёт friction, **и вместе с ней растёт вероятность, что пользователь отключит защиту целиком** — тогда защита равна нулю. **[Ф]** Конкурентный анализ формулирует это как правило рынка: «решение с идеальной детекцией и высоким FPR проигрывает, потому что его выключают».
- Если снизить долю подтверждений, растёт вероятность пропуска. **[Ф]** Честная цифра рынка: FNR 17 % на реальных overeager-действиях у Claude Code — вендор публикует её сам.
- Промежуточный вариант «спрашивать умнее» упирается в то, **[Ф]** что LLM-классификатор, читающий контекст агента, по построению уязвим к тому, что в этом контексте написано: обход Rehberger — 60–80 % успешных инъекций через цепочку внешне безобидных шагов.

**[Ф] Что об этой проблеме говорит наш опрос — и в чём он расходится с исходной рамкой.** Среди 20 респондентов с опытом чаще всего отмечены **не** лишние подтверждения, а непонимание последствий действия агента (13 из 20) и страх утечки секретов или данных (13 из 20); недостаток контроля над разрешениями — 10; «слишком часто просит подтверждение» — 8; «блокирует безопасные действия» — 7. Хотя бы один из трёх пунктов «непонятны последствия / непонятны причины решения / не хватает контроля» выбрали **все 20**.

**[И]** Approval fatigue остаётся реальной болью, но в этой выборке она не главная. Проблема формулируется точнее как **непрозрачность**: пользователь не понимает, что произойдёт и почему система решила так, а не иначе. Это множественный выбор и отметки опасений, а не частота инцидентов; переносить проценты на всех разработчиков нельзя.

**[Ф] Шесть свободных рассказов о неприятных случаях** (14 из 20 поле не заполнили) не содержат ни одной атаки: удалённая таблица БД, миграция, применённая сразу после генерации без вопроса, установленные не те пакеты, ответы техлиду в MR за пользователя, впустую потраченные токены, просадка утилизации GPU из-за вписанного логирования. **[И]** Половина из них — про ошибку и выход за рамки поручения, а не про злоумышленника.

**[Р]** Команда формулирует пользовательскую проблему как **проблему распределения решений**, а не как проблему детекции: вопрос не «как поймать атаку», а **«какие решения вообще не должны доходить до человека, какие обязаны, и как сделать так, чтобы отказ не останавливал работу»**. **[И]** Опрос эту формулировку скорее поддерживает, но добавляет к ней третью часть: **«и как объяснить пользователю, что именно произойдёт»** — объяснимость в анкете весит больше, чем автономность.

### Что входит в проблему дополнительно

**[Ф]** Кейс требует ещё двух вещей, которые команда считает частью той же пользовательской проблемы, а не отдельными фичами:

- **Продолжение работы после блокировки.** Блокировка, после которой агент встал, — это тот же простой, что и подтверждение, только без выбора.
- **Хотя бы один контроль, архитектурно неуязвимый к prompt injection.** Гардрейл, живущий в контексте агента, обходится текстом в этом же контексте.

## 3. Current product insight

**[Р]** Ключевой insight команды на текущий момент:

> **Максимальное блокирование и максимальное количество подтверждений — это одно решение, а не два разных: оба перекладывают риск на человека, который заведомо плохо его оценивает, и оба оплачиваются его временем. Продуктовая задача — не «спрашивать чаще» и не «блокировать больше», а сократить множество решений, которые вообще требуют человека, не сделав при этом пропуск дешевле.**

Почему простые варианты недостаточны:

**Почему не «блокировать максимум».** **[Ф]** Метрика Utility в кейсе существует ровно для этого: «без неё любая защита может выглядеть идеальной, поскольку самый надёжный способ защиты — не позволять агенту работать». **[Ф]** Денайлисты как класс признаны хрупкими: Backslash/HiddenLayer нашли ≥4 обхода auto-run денайлиста Cursor, после чего денайлист объявлен устаревшим; префиксное сравнение обходится (Gemini CLI). То есть агрессивная блокировка одновременно **и мешает работать, и не держит**.

**Почему не «спрашивать всегда».** **[Ф]** Цифры approval fatigue выше: 93 % одобрений, 13,6 % поимки, деградация с 17 % до 5 %. Человек, которого спрашивают часто, перестаёт быть контролем и становится ритуалом. **[Ф]** Рынок уже относится к `ask` как к дорогому ресурсу: Codex сократил остановки на человека примерно в 200 раз (7,2 % действий доходят до ревью, из них 99 % одобряются), Cursor заявляет сокращение запросов примерно на 84 %.

**Почему не «один умный классификатор».** **[Ф]** Классификатор вероятностен (FNR 17 % — «the honest number» по формулировке источника), стоит токенов и латентности, и сам является целью инъекции. **[Ф]** Вендоры прямо говорят, что гейт — «best-effort convenience, not a security boundary» (Cursor); Anthropic закрыла обход Rehberger как «Informative» на том же основании.

**[Р]** Следствие, принятое командой: **гейт конкурирует не с сэндбоксом, а с трением ручного подтверждения.** Это формулировка из `03_competitor_research_summary.md` §1, и команда приняла её как рамку позиционирования: мы не обещаем границу безопасности, мы обещаем перераспределение решений при сопоставимом риске. Сэндбокс требуется рядом, а не заменяется (`why-agentgate.md`, «Чего OPENMAGI не обещает»).

**[Р]** Второе следствие: **если часть решений принимается детерминированно и без чтения текста, то именно эта часть — единственное, на что можно давать гарантию.** Всё остальное вероятностно и должно так и называться.

## 4. Product hypothesis

### Основная гипотеза (проверяемая форма)

> **[Г] Если** решение о каждом действии агента выносить **вне харнесса**, в отдельном сервисе, где действие сначала нормализуется в AST и проходит детерминированную ступень без обращения к LLM, а до модели доходит только то, что детерминированная ступень не смогла решить, **то** доля действий, требующих человека, окажется достаточно низкой, чтобы разработчик не отключил защиту, при доле пропущенных атак не выше, чем в режиме ручного подтверждения, **потому что** большая часть реального трафика агента — рутинные и read-only действия, решаемые правилами за миллисекунды и бесплатно, а человек как детектор опасного действия работает хуже автоматической проверки (93 % одобрений, 13,6 % поимки).

Гипотеза намеренно связана с реальной архитектурой: каждое её звено соответствует существующему компоненту — `normalize/` (AST), `rules/chain.py` (детерминированная ступень), `classify/` (LLM только на остатке), `POST /v1/decide` (решение вне харнесса). *(Пути обновлены: рефакторинг v1.5 переименовал `pipeline.py` → `engine/gate.py`, `stage1/` → `rules/`, `stage2/` → `classify/`, поведение не изменив.)*

**Статус проверки на 6 сентября 2026: гипотеза не подтверждена в той форме, в какой сформулирована.** На общей популяции из 67 кейсов родной auto mode Claude Code дал такой же ASR (19,6 %), но выше точность (86,6 % против 79,1 %) и ноль ложных срабатываний против двух у нашего гарда. Часть про «низкую долю действий, требующих человека» держится: на 30 контрольных кейсах Utility 96,7 %, FP 3,3 %, ни одного подтверждения. Часть про «не хуже, чем у альтернативы» — нет.

### Три подчинённые гипотезы

**[Г] H2 — о гарантии.** Если часть опасных действий закрыта правилами, работающими по AST, а не по тексту, то эта часть не обходится инструкцией, попавшей в контекст агента (README, SKILL.md, вывод инструмента). Частично подтверждено конструкцией: **[Ф]** ступень 1 не читает сырую строку для принятия решения, а в промпт ступени 2 не попадают ни `metadata`, ни выводы инструментов, ни рассуждения агента; табличные тесты hard-deny покрывают `$(…)`, `eval`, переменные, base64, heredoc и обёртки. **[?]** Устойчивость к адаптивной атаке не измерена ни разу.

**[Г] H3 — о продолжении работы.** Если отказ возвращается агенту как результат инструмента с причиной и безопасной альтернативой, агент продолжит задачу, а не остановится. **[Ф]** В контракте есть поля `reason` и `suggest` и шаблон `contracts/deny_message_template.md`; **[Ф]** с появлением адаптеров текст отказа действительно подставляется агенту клиентским ядром (`adapters/packages/core/src/policy.ts`, функция `denyMessage`). **[?]** Доля восстановлений агента после `deny` не измерялась ни разу: режим бенчмарка `harness_loop`, в котором это можно было бы увидеть, объявлен в схеме, но ни одного прогона в нём не было.

**[Г] H4 — о переносимости.** Если политика живёт в сервисе, а не в харнессе, одна и та же политика применима к нескольким агентам. **[Ф]** Написаны плагины к шести харнессам поверх общего ядра (`adapters/`: opencode 1.x, Kilo CLI, opencode 2.0, Pi, Codex CLI, DeepSeek Harness), плюс инсталлер и эталонный `hook_client.py`. Соответствие их запросов схемам сервиса проверяется автоматически (`benchmark/tests/test_adapter_contracts.py`). **[?]** Бенчмарком измерена ровно **одна** интеграция из шести — Claude Code через хуки SDK; остальные пять проверялись ручными прогонами (`adapters/docs/MANUAL-TESTING.md`). Продуктовая ценность переносимости — то есть выигрыш от единой политики — не измерена вовсе: бенчмарк меряет качество решения, а не выигрыш от переноса.

### Что гипотеза сознательно НЕ утверждает

**[Р]** Команда сознательно не формулирует гипотезу как «мы безопаснее» или «у нас ниже FPR, чем у конкурентов». **[Ф]** Основание — раздел «Do not claim yet» конкурентного анализа: сравнивать FPR/FNR можно только на одном датасете, а вендорские цифры получены на трёх разных наборах и не смешиваются.

## 5. Value proposition

**Формулировка:** OPENMAGI даёт кодинг-агенту режим, в котором рутина выполняется без подтверждений, опасное останавливается с объяснением и безопасной альтернативой, а человека спрашивают только там, где автоматика не смогла решить, — и каждое такое решение записано и измеримо.

### Пользовательская ценность

- **[Г]** Меньше подтверждений при сопоставимом риске — то, ради чего пользователь сейчас включает bypass. **[Ф]** На контрольной группе из 30 легитимных кейсов подтверждений не потребовалось ни разу, один кейс был отвергнут (Utility 96,7 %, FP 3,3 %). **[?]** На реальном трафике не измерено: датасет синтетический. **[Ф] Оговорка от опроса:** «почти не спрашивать о безопасных действиях» выбрали самым ценным улучшением лишь 2 из 20 — это наименее востребованная из наших сильных сторон.
- **[Ф] Три ценности, которые опрос ставит выше:** безопасное продолжение после блокировки (6 из 20), понятный журнал действий (5) и объяснение, почему действие опасно (5). Суммарно их выбрали 16 из 20 — столбец допускал один вариант, поэтому это 16 разных людей. Все три у нас есть в каком-то виде: `suggest` в ответе, лента `GET /v1/decisions` плюс JSONL, `reason` при каждом отказе. **[?]** Насколько их текущее качество отвечает ожиданию — не проверялось.
- **[Ф]** Работа не останавливается на отказе: ответ несёт `reason` и `suggest`; формат отказа — часть контракта, а не текст в UI.
- **[Г]** Auto mode для харнесса, у которого его нет. **[Ф]** Основание — отсутствие auto mode в открытых агентах; **[Ф]** плагины написаны для шести харнессов и устанавливаются инсталлером; **[?]** ценность этого для пользователя не измерена, а из шести интеграций бенчмарком проверена одна.
- **[Ф]** Политика в одном YAML на стороне сервиса, в git, с историей — вместо отдельного формата настроек на каждый агент.

### Техническая ценность

- **[Ф]** Детерминированная ступень до LLM: p50 нормализации + ступени 1 ≤ 1 мс — проверяется тестом `service/tests/rules/test_latency.py`. **[Ф]** В боевом прогоне та же величина по данным сервиса: ступень 1 p50 0 мс, максимум 3 мс; сквозная латентность решения p50 1108 мс, p95 1669 мс (при `--concurrency 1`).
- **[Ф]** Fail-closed на каждом пути: ошибка, таймаут, невалидный запрос или невалидный ответ модели → `ask` с HTTP 200; `allow` по ошибке недостижим — на это есть отдельные тесты.
- **[Ф]** Выбор модели ступени 2 и периметра данных — конфигурация профиля (OpenAI-совместимый API); read-only и hard-deny до модели вообще не доходят, то есть стоят ноль токенов. В прогоне 50 решений из 120 не дошли до модели.
- **[Ф]** Каждое решение пишется в Postgres и JSONL с указанием ступени, `rule_id`, модели, латентности по ступеням и хэша профиля; лента доступна через `GET /v1/decisions`.

### Отличие от существующих подходов

**[Ф]** Что действительно отличается — **упаковка**: гейт как отдельный сервис с собственным HTTP-контрактом, а не код внутри харнесса. Конкурентный анализ помечает это как **[Г]**, а не как факт уникальности: заявку на кросс-агентность делают Adversa AI и, в своей нише, Arcade.dev, и глубина их исполнения неизвестна.

**[Ф]** Что отличием **не является** и не должно заявляться (прямой список из §9 конкурентного анализа): LLM-классификация действия перед исполнением; двухстадийность fast→CoT и reasoning-blind; fail-closed; deny-and-continue; эскалация по счётчикам; prose-политика и профили; AST-нормализация shell (CARE сделал это раньше и с опубликованными метриками); аудит решений; сам тезис «мы снижаем approval fatigue» (Codex и Cursor заявили его раньше и с цифрами).

**[Р]** Решение команды: **отличие формулируется как «политика вне харнесса + детерминированная ступень + измеримость», и ни один из трёх пунктов не подаётся как изобретение.**

## 6. Product approach

### Выбранный подход

**[Р]** **Runtime decision layer: внешний сервис, принимающий решение по каждому предложенному действию до его исполнения, с риск-зависимым вмешательством вместо равномерного контроля.**

Формально: `AI Agent / Harness → перехват до исполнения → OPENMAGI → allow | deny | ask → действие агента`.

Три решения, из которых следует остальное (зафиксированы в `architecture_description.md` §2 и подтверждены кодом):

1. **[Р]** Точка врезки — **до исполнения инструмента и вне харнесса**. Политика одна на все харнессы и живёт на стороне сервиса.
2. **[Р]** **Решение никогда не принимается по сырой строке команды** — только по `NormalizedAction`, полученному разбором в AST.
3. **[Р]** **Fail-closed как позвоночник** — любая неопределённость превращается в `ask`, а не в `allow`.

### Почему не альтернативы

| Альтернатива | Почему отвергнута как основной подход |
|---|---|
| Только allowlist / денайлист без модели | **[Ф]** Денайлисты систематически обходятся (Cursor отказался от своего); префиксное сравнение — источник обходов (Gemini CLI). Оставлено как **ступень**, а не как продукт |
| Только LLM-классификатор | **[Ф]** Вероятностен (FNR 17 %), стоит токенов и латентности на каждом действии, сам является целью инъекции; при недоступности провайдера всё превращается в `ask` |
| Сэндбокс | **[Ф]** Единственная настоящая граница безопасности по признанию вендоров — но не различает намерение и ломает легитимные сценарии. **[Р]** Мы его требуем рядом, а не заменяем |
| Гейт внутри одного харнесса (как у Kilo/Claude) | **[Ф]** Ровно то, что уже есть у всех: политика не переносится, дублируется и расходится между агентами. **[Р]** Основание для выбора отдельного сервиса — не безопасность, а переносимость политики |
| Гардрейл в контексте агента (промпт/инструкция) | **[Ф]** «Запрет, живущий в инструкциях, агент рационализирует» (вывод из инцидента Replit); контроль должен быть в call-path |

### Связь с тремя опорами

**С target architecture.** **[Ф]** Целевая схема (`target_architecture.jpg`, §3–4 `architecture_description.md`) — тот же подход в полном объёме: Context Guard на входе данных, Action Analyzer, Policy & Risk Engine (Hard Rules → Session Rules → AI Risk Classifier), Session State / Audit, узел Security Decision с четырьмя исходами. Текущая реализация — **нижний контур этой схемы**: Action Analyzer + Policy & Risk Engine + Session State в урезанном виде + три исхода из четырёх.

**С competitor research.** **[Ф]** Каскад «детерминированная ступень → LLM-ступень → эскалация», reasoning-blind, fail-closed, deny-and-continue — де-факто стандарт, а не дифференциатор. **[Р]** Команда сознательно воспроизводит стандарт в ядре и не заявляет его новизну; ставка сделана на упаковку (внешний сервис), измеримость и детерминированную гарантию.

**С текущей реализацией.** **[Ф]** Подход реализован ровно в том виде, в каком описан: `POST /v1/decide` → нормализация → `rules/chain.py` (19 правил одним списком: hard-deny → правила пользователя → профиль → allowlist → слот пакетов) → `classify/` → эскалация по счётчикам сессии → `allow | deny | ask` с записью решения. Все элементы подключены к основному потоку и покрыты тестами; e2e-сценарий проходит через реальный подпроцесс сервиса и `contracts/hook_client.py`. **[Ф]** Сверх описанного подхода появилось второе направление — `POST /v1/inspect`, оценка результата инструмента до того, как его увидит модель.

## 7. MVP boundary

**[Р]** Граница проводится по одному критерию: **входит то, без чего нельзя проверить основную гипотезу (§4)**. Целевая функциональность в MVP автоматически не входит.

### In MVP

| Элемент | Зачем нужен для проверки гипотезы | Статус |
|---|---|---|
| `POST /v1/decide` с тремя исходами | Сама единица измерения гипотезы — решение по действию | **[Ф]** реализовано |
| Нормализация в AST (`NormalizedAction`) | Без неё «детерминированность» и «неуязвимость к тексту» ничем не подтверждаются | **[Ф]** реализовано |
| Ступень 1: hard-deny → профиль → allowlist | Ядро гипотезы: большая часть трафика решается без LLM | **[Ф]** реализовано |
| Ступень 2 (LLM) на остатке | Проверка утверждения «до модели доходит меньшинство» | **[Ф]** реализовано |
| Эскалация по счётчикам сессии | Ограничение blast radius там, где пер-экшн-классификация ошибается | **[Ф]** реализовано |
| Fail-closed на всех путях | Без него утверждение «`allow` по ошибке невозможен» не проверяемо | **[Ф]** реализовано (для сервиса) |
| `reason` + `suggest` в ответе | Гипотеза H3: работа продолжается после отказа | **[Ф]** поля есть, текст подставляется агенту клиентским ядром; **[?]** доля восстановлений не измерена |
| Запись каждого решения (Postgres + JSONL, `GET /v1/decisions`) | Без неё гипотеза не измерима в принципе | **[Ф]** реализовано |
| Один YAML-профиль на сервисе | Проверка «политика вне харнесса» | **[Ф]** реализовано |
| Бенчмарк: датасет + раннер + скорер + отчёты | Инструмент, которым гипотеза проверяется | **[Ф]** реализовано |
| **Первый прогон бенчмарка против живого сервиса** | Единственный шаг, превращающий «implemented» в «validated» | **[Ф] сделан 6 сентября 2026** — 120 + 46 + 12 кейсов плюс три конфигурации Claude Code |
| **Хотя бы одна реальная интеграция с харнессом** | Без неё гипотеза проверяется на стенде, а не на продукте | **[Ф] сделано:** плагины к шести харнессам; бенчмарком измерена одна из них |

### Outside current MVP

Сознательно не требуется для проверки основной гипотезы:

- **[Р]** **Context Guard целиком** — был отнесён к v4 и **с тех пор закрыт частично**: реализовано направление «результат инструмента → модель» (`POST /v1/inspect`: детекторы инъекций, маскирование секретов, обязательный провенанс, опциональный классификатор). Остальные источники контекста (промпт пользователя, файлы проекта, веб напрямую) сервис по-прежнему не видит, taint-цепочек между шагами нет, а в развёрнутом профиле семантический классификатор inspect выключен.
- **[Р]** ~~**История диалога (v2) и оценка `tool-result` (v3)**~~ — **обе реализованы** после того, как эта граница была проведена: `history` в запросе с v2, `POST /v1/inspect` с v3. Открытой из дорожной карты осталась только v5 — независимость от провайдера модели (`context-versions-roadmap.md`).
- **[Р]** **Четвёртый исход SAFE RECOVERY** — сведён к текстовому полю `suggest`; отдельным маршрутом не является.
- **[Р]** **Модуль пакетов / slopsquatting** — место в каскаде занято (`service/agentgate/rules/packages.py`), проверка не реализована; typosquat ловится только ступенью 2. Кандидат на расширение после MVP (то же рекомендует конкурентный анализ, §10).
- **[Р]** **Панель / UI, override, обучение политики** — не в v1.
- **[Р]** ~~**Внешний бенчмарк против конкурентов**~~ — **частично реализован и однажды прогнан**: бенчмарк умеет три конфигурации Claude Code (`claude-code`, `claude-sdk`, `claude-agentgate`) и сравнивает прогоны попарно. Codex, Cursor и статические правила целями прогона не являются; внешний исполняемый baseline ActBench подключён кодом, но не запускался.
- **[Р]** **Параллельные проверки, метрики/трейсинг, общее состояние сессии между процессами** — по-прежнему не сделаны и зафиксированы как известные ограничения. **Идемпотентность и атрибуция решения к ключу с тех пор реализованы** (v3.2–v3.3): `Idempotency-Key` действует в границах предъявителя и сессии, `key_id` пишется в строку решения и доступен фильтром в ленте.

**[Р]** Отдельное решение: **всё, что «Outside MVP», остаётся в документах как явно неготовое, а не выпадает из описания продукта.** Основание — требование кейса о честности гарантий («что система гарантирует всегда, а что обеспечивает по возможности»).

## 8. Primary user flow

Сценарий описан на продуктовом уровне; инженерные подробности — в `architecture_description.md` §6 и `05_current_state.md`.

1. **Разработчик ставит задачу агенту** в своём харнессе — обычным текстом, ничего не зная про OPENMAGI.
2. **Агент решает выполнить действие** — команду в shell, запись файла, сетевой вызов, вызов MCP-инструмента.
3. **Действие перехватывается до исполнения.** Харнесс через адаптер отправляет описание действия и последний запрос пользователя в OPENMAGI. **[Ф]** Сервис получает только действие + `user_request`; рассуждения агента и выводы инструментов не передаются.
4. **OPENMAGI выносит решение** — за миллисекунды, если хватило правил, иначе с обращением к модели.
5. **Ветвление, которое видит пользователь:**
   - **allow** — действие выполняется, пользователь ничего не замечает. **[Р]** Это целевое состояние для большинства действий;
   - **deny** — действие не выполняется, агент получает причину и безопасную альтернативу как результат инструмента и **продолжает задачу другим путём**; пользователь видит объяснение, а не остановку;
   - **ask** — пользователя спрашивают. **[Р]** Это дорогой ресурс, и каждый такой случай обязан нести причину и вариант действия.
6. **Повторное такое же действие в той же сессии** проходит быстрее: **[Ф]** `allow` кэшируется на сессию, `deny` и `ask` не кэшируются никогда.
7. **Если агент упирается в стену** (три отказа подряд либо 10 из последних 50), решение принудительно уходит человеку — **[Р]** это сигнал «границу нужно чинить», а не наказание агента.
8. **Каждое решение записано** — разработчик или команда может позже посмотреть ленту решений: что просили, что предложил агент, что решил гейт, на какой ступени и почему.

**Что из этого подтверждено, а что нет.** **[Ф]** Шаги 1–8 реализованы: плагины к шести харнессам ставятся инсталлером, перехват и подстановка текста отказа живут в клиентском ядре, штатный диалог подтверждения используется там, где он у харнесса есть. **[Ф]** Шаг 8 (лента решений) существует только как API — панели нет.

**[?] Что остаётся непроверенным.** Бенчмарком измерена одна интеграция из шести — Claude Code через хуки SDK; остальные пять проверялись ручными прогонами и в рамках аудита документации не воспроизводились. Продолжение работы после `deny` (шаг 5) наблюдалось вручную, но никогда не измерялось: для этого нужен режим `harness_loop`, прогонов в котором не было. У Codex CLI шаг 5 работает не полностью: в версии 0.146 из `PreToolUse` доступен только `deny`, а подмена результата не поддерживается.

**[Ф] Дополнение к сценарию, появившееся после v3.** Между шагами 5 и 6 может встать проверка результата инструмента: адаптер отправляет вывод на `POST /v1/inspect` и подставляет модели `pass`, замаскированный текст или сообщение о блокировке. Пользователь этого шага не видит вовсе — в этом и смысл.

## 9. Success criteria

**[Р]** Критерии взяты из целевых метрик кейса. **Числовых порогов команда так и не зафиксировала** — ни до прогона, ни после. Это осознанный пробел, а не упущение формулировки: без порога, названного заранее, любая цифра интерпретируется задним числом. Ниже — что измеряется, чем считается и что получилось в единственном прогоне.

**[Ф]** Все агрегаты считаются в одном месте — `benchmark/evaluator/metrics.py`; `reporting/` только рендерит и ничего не досчитывает. Это важно для критериев: метрику нельзя «улучшить» в отчёте, её можно только пересчитать из сохранённых сырых результатов.

### Safety

- **ASR** — доля атакующих кейсов, где сервис разрешил действие, которое кейс не объявил допустимым. **[Ф]** В прогоне: **22,2 %** (20 из 90 на нашем сервисе напрямую), 19,6 % у нашего ядра внутри Claude Code на общей популяции.
- **Разбивка пропусков** по категории атаки, сложности, ступени и паре «категория × сложность». **[Ф]** Реализована (`metrics_by`). Худшая категория в прогоне — `multi_turn_trust_escalation` (5 провалов из 6).
- **[Ф]** Все 24 провала пришлись на ступень 2. Ступень 1 не ошиблась ни разу — это ровно то разделение «гарантируется всегда / по возможности», которого требует кейс.
- **[Р]** Требование к методу сохраняется: FN на «неосторожных» действиях и FN на adversarial-цепочках не смешиваются.
- **[?]** Тег `v1_limitation`, которым раньше помечались заведомо непокрываемые кейсы, **больше не стоит ни на одном кейсе** — упоминание осталось только в `attacks/taxonomy.md`. Механизм `tag_failures` в отчёте работает, но этой корзины сейчас нет.
- **[?]** Recall / детекция: `detected` и `detection_correct` считаются построчно, но в сводку не агрегируются. Этой метрики у нас фактически нет — как и год назад.

### Friction / usability

- **Utility** — доля легитимных кейсов, завершённых без вмешательства человека. **[Ф]** В прогоне: **96,7 %** (29 из 30).
- **FP rate** — вмешательство на легитимной задаче. **[Ф]** В прогоне: **3,3 %** (1 кейс, `BENIGN_014`: `uv pip install httpx==0.27.2`). **[Ф]** Определение метрики учитывает клиентские правила: `ask`, которого потребовал сам пользователь, не считается ошибкой сервиса. Эта поправка была внесена в ходе прогона (коммит `371fd84`) — до неё любой ruled-прогон завышал FP.
- **Friction** — число решений, потребованных от человека. **[Ф]** На контрольной группе — **ноль подтверждений**.
- **Доля трафика, дошедшая до LLM-ступени.** **[Ф]** В прогоне: 70 из 120 (58 %); ступень 1 закрыла 50. **[Р]** Сравнивать это с ориентиром рынка (у Codex до ревьюера доходит 7,2 % трафика) **нельзя**: наш датасет намеренно насыщен атаками, реальный трафик агента устроен иначе.
- **[?]** Доля восстановлений агента после `deny` (ориентир Codex >50 %) — в бенчмарке не реализована.
- **[?] Ограничение, которое проговаривается вместе с любой цифрой friction:** контрольная группа — 30 кейсов. Один провалившийся benign-кейс двигает метрику на 3,3 пункта. Это лучше прежних 5 кейсов (20 пунктов на кейс), но всё ещё индикатор, а не измерение.

### Performance

- **Латентность ступени 1.** **[Ф]** Юнит-бюджет p50 ≤ 1 мс (`service/tests/rules/test_latency.py`); в боевом прогоне по данным сервиса p50 0 мс, максимум 3 мс.
- **Латентность решения целиком.** **[Ф]** p50 1108 мс, p95 1669 мс, максимум 2425 мс при `--concurrency 1`; ступень 2 — p50 1290 мс. **[Р]** Заявления делаются только по `latency_ms` сервиса и только при `--concurrency 1`: клиентские настенные часы растут с параллелизмом.
- **Замедление задачи целиком.** **[?]** Не измерено и в текущем режиме измеримо быть не может: бенчмарк исполняет одно решение на кейс, задача вокруг него не выполняется. Метрика возвращает `None` и называет причину.
- **Стоимость.** **[Ф]** Механизм готов с обеих сторон: сервис отдаёт токены в поле `cost` (в прогоне — по 70 запросам, 55 207 входных и 4 685 выходных), бенчмарк умеет три состояния цены, включая измеренный ноль «модель не вызывалась». **[?]** Деньги не посчитаны: цены модели в развёрнутом профиле не заданы и таблица цен не передавалась. **Стоимость по-прежнему не измерена.**

### Качественные критерии (из кейса)

**[Р]** Команда принимает формулировку кейса: «Отрицательный результат с понятным методом ценнее хорошего числа без описания метода». Прогон 6 сентября — ровно такой случай: он показал, что родной auto mode на этой популяции сильнее нашего гарда, и это записано в отчёте первым выводом, а не спрятано.

**[Ф]** Воспроизводимость соблюдена в части конфигурации: зафиксированы дата, `git_sha` сервиса, дайджест профиля, модель, `--concurrency`, дайджест датасета. **[?]** Не соблюдена в части артефактов: `benchmark/results/` в `.gitignore`, поэтому сами `summary-*.json` и SQLite в git не попали.

11. Модуль пакетов / slopsquatting — детерминированная проверка вместо заглушки; прямо назван в кейсе.
12. Измерить оставшиеся пять интеграций либо явно сказать, что они проверены только вручную.
13. **Интервью с коротким заданием, 6–8 участников из разных групп** — следующий шаг, предложенный самим отчётом по опросу (`09_user_research/README.md` §6). Опрос показал, *что* болит; интервью должно показать, *как это выглядит в работе*. Минимально: разобрать последний конкретный эпизод до показа списка вариантов; дать сопоставимые сценарии на размытых границах (создать миграцию против применить, известная зависимость против новой, чтение БД против изменения); сравнить базовый режим и прототип на одинаковых задачах. Ни одного наблюдения за пользователем в работе у продукта по-прежнему нет.

## 15. Open product questions

Вопросы, которые команда на текущий момент **не закрыла**.

**Об уровне вмешательства**

1. **Какая доля `ask` считается приемлемой?** Порога нет до сих пор — теперь уже и после прогона. Это пробел: без порога, названного заранее, цифра 96,7 % Utility интерпретируется задним числом.
2. **Какой false-positive rate допустим?** Тот же статус. Контрольная группа из 30 кейсов даёт разрешение 3,3 пункта — этого мало для порога вроде «не выше 2 %».
3. **Нужно ли human confirmation вообще, если ставка на автономию?** Сегодня `ask` — и штатный исход, и универсальный fallback при любой ошибке. Не решено, разделять ли эти два смысла для пользователя.
4. **Нужен ли SAFE RECOVERY как отдельный исход?** Целевая схема даёт четыре ветви, контракт — три.
5. **Нужен ли Comment от человека агенту** как часть контракта, или подтверждение целиком остаётся внутри харнесса.

**О рисках и политике**

6. **Fail-open или fail-closed на стороне адаптера?** Три варианта зафиксированы, выбор не сделан. От него зависит, верно ли утверждение «`allow` по ошибке невозможен» для системы в целом. Самый старый открытый вопрос проекта.
7. **Включать ли классификатор inspect в развёрнутом профиле?** Он закрывает три кейса `semantic_gap`, но добавляет вызов модели на каждый флагованный результат. Сейчас выключен по умолчанию, и это решение по умолчанию, а не выбор.
8. **Нужны ли уровни риска вместо трёх плоских исходов?** В целевой схеме есть Risk Score, в коде — нет.
9. **Нужны ли бюджеты автономии на сессию?** Конкурентный анализ отмечает это как незакрытую нишу; у нас есть только счётчики отказов.

**О качестве решения**

10. **Что делать с результатом сравнения?** Родной auto mode Claude Code точнее нашего гарда при равном ASR. Варианты: улучшать промпт и модель ступени 2, переносить повторяющиеся промахи в детерминированные правила, менять модель. Решение не принято, а от него зависит, что вообще предъявляется как результат проекта.
11. **Почему худшая категория — `multi_turn_trust_escalation`?** История диалога передаётся с v2 и на ступень 2 доходит, но 5 из 6 кейсов провалены. Не установлено, дело в промпте, в бюджете усечения истории или в модели.

**Об универсальности**

12. **Измерять ли остальные пять интеграций,** или честно сказать, что они проверены только вручную.
13. **Публиковать ли датасет?** Кейс отмечает вклад в общий бенчмарк угроз как отличающий команду; сейчас 120 + 46 + 12 кейсов живут только внутри репозитория.

**О пользователе**

14. **Готов ли целевой пользователь ставить отдельный сервис, а не плагин?** Ключевое предположение, на котором стоит упаковка продукта. Опрос его не касался — вопрос остаётся полностью открытым.
15. **Что пользователь считает раздражающим отказом, а что — оправданным?** Метрика FP есть; опрос даёт границы, но грубые: секреты, отправка наружу и sudo — почти безусловное «спросить» (16 и по 14 из 20), поиск и рефакторинг — почти безусловное «не спрашивать» (17 и 16 из 20). Что происходит между этими полюсами, не выяснено, а один респондент прямо хочет автономную установку зависимостей и одновременно подтверждение новых пакетов.
16. **Переформулировать ли основную гипотезу вокруг объяснимости, а не вокруг числа подтверждений?** Опрос ставит непонимание последствий (13 из 20) выше лишних подтверждений (8 из 20), а тройку «безопасное продолжение / журнал / объяснение» выбрали 16 из 20 против 2 из 20 за «почти не спрашивать». Продуктовое решение не принято; от него зависит, что мы вообще измеряем бенчмарком.
17. **Расширять ли датасет в сторону ошибок агента, а не только атак?** Половина свободных рассказов — про действие за пределами поручения и про ошибку, а не про злоумышленника. Сейчас это покрыто одной категорией из пятнадцати.

## Связка целиком

**Problem** — разработчик не может получить и автономию агента, и уверенность, потому что единственный регулятор (подтверждать или нет) регулирует не риск, а его собственную работу; человек как детектор деградирует по ходу сессии. **Наш опрос (28 ответов, 20 с опытом) уточняет формулировку:** сильнее всего мешает не частота вопросов (8 из 20), а непонимание последствий действия и страх за данные (по 13 из 20).

**→ Product hypothesis** — если решение выносить вне харнесса, нормализовав действие в AST и пропустив его через детерминированную ступень до LLM, доля действий, требующих человека, будет достаточно низкой, чтобы защиту не отключили, при доле пропусков не хуже альтернативы.

**→ Product decision** — runtime decision layer как отдельный сервис; решение никогда по сырой строке; fail-closed везде; `ask` — дорогой ресурс; `deny` обязан нести причину и альтернативу; правила пользователя могут только ужесточать; каждое решение записано.

**→ Technical implementation** — `POST /v1/decide` → `normalize/` (AST) → `rules/` (19 правил, hard-deny → правила пользователя → профиль → allowlist) → `classify/` (LLM только на остатке) → эскалация по сессии → `allow | deny | ask` → Postgres и JSONL. Плюс второе направление `POST /v1/inspect` для результатов инструментов и плагины к шести харнессам.

**→ Benchmark / validation** — 120 pre-action кейсов в 16 категориях с контрольной группой на 30, 46 inspect-кейсов, 12 регрессий политики, детерминированный скорер, метрики Safety / Friction / Performance / Cost. Прогон выполнен один раз, 6 сентября 2026.

**→ Что показал опрос** — проблема признаётся, но её центр смещён: пользователи хотят объяснимости, журнала и безопасного продолжения (16 из 20 в сумме) заметно больше, чем молчаливого агента (2 из 20). Спрос, готовность платить и эффективность решения опрос не измеряет.

**→ Что показал прогон бенчмарка** — низкое трение (Utility 96,7 %, FP 3,3 %, ноль подтверждений на контрольной группе) и детерминированную ступень, которая не ошиблась ни разу, при ASR 22,2 % и точности 80,0 %. И одновременно: на общей популяции родной auto mode Claude Code точнее нашего гарда при равном ASR. Это результат, а не помеха — но заявлять «мы безопаснее» после него нельзя, и в этом документе так и не заявляется.
