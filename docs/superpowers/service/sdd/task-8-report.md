# Задача 8 — OpenAPI генерируется приложением

Ветка `refactor/solid-v1.5`. Реализацию вёл субагент; он **упал на ошибке аутентификации API (403)** ровно на фразе «Now the full triage of the `openapi.yaml` diff», то есть успел сделать работу и не успел её описать. Код остался в рабочем дереве в зелёном состоянии (665 тестов, код возврата 0). Триаж диффа, проверку и завершение задачи выполнил контроллер; ниже честно помечено, что чьё.

## Что построено

| Файл | Было | Стало |
|---|---|---|
| `scripts/export_openapi.py` | 886 строк, из них ≈600 — проза в строковых константах и `_paths()`, собранный руками | **96 строк**: собирает сервис, вызывает `app.openapi()`, пишет YAML |
| `agentgate/api/openapi.py` | — | 105 строк: три вещи, которые FastAPI выразить не умеет |
| `agentgate/api/examples.py` | — | 163 строки: примеры запросов и ответов, объявленные на маршрутах |

Проза переехала из констант экспортёра в `Field(description=...)` на моделях и в `summary`/`description` на маршрутах. Теперь одна правка обновляет и код, и документ — расхождение, которое `contracts/README.md` признавал, стало невыразимым.

`agentgate/api/openapi.py` добавляет к документу FastAPI ровно три вещи и объясняет каждую в docstring: необязательность bearer-аутентификации (FastAPI умеет только пооперационные требования), схемы запроса (`DecideRequest` не стоит в сигнатуре маршрута — именно поэтому невалидное тело даёт 200 `ask`, а не 422, — и FastAPI её не собирает), и примеры в исходном виде (кодировщик FastAPI выбрасывает `null`, а `rule_id`, `model` и постадийные задержки в большинстве настоящих ответов именно `null`).

## Триаж диффа `contracts/` — выполнен контроллером

Правило задачи: **закоммиченный контракт — источник истины; расхождение по умолчанию означает, что неверна модель.**

### 1. `decide_request.schema.json` и `decide_response.schema.json`

Бриф требовал, чтобы они не менялись **вообще**. Они изменились. Проверка строгая: обе схемы разобраны, из них рекурсивно удалены все ключи `description`, результаты сравнены со старыми версиями.

```
contracts/decide_request.schema.json   без description идентичны: True
contracts/decide_response.schema.json  без description идентичны: True
```

Ни одного поля, типа, ограничения или обязательности не тронуто — добавлены только описания. **Требование брифа было сформулировано слишком грубо** и должно было звучать как «ни одно поле, тип или обязательность не меняются»: перенос прозы на модель неизбежно добавляет `description` в порождаемую JSON Schema, и это ровно то, ради чего задача существует. Изменение принято.

### 2. `openapi.yaml`: пути и коды ответов

**Этот раздел переписан после ревью. Первая его версия содержала круговое рассуждение и была неверна; ниже сказано, в чём именно, потому что документ служит пакетом для согласования контракта и обязан быть точным.**

Пути не изменились: `/healthz`, `/v1/decide`, `/v1/decisions`, `/v1/profiles/{id}`.

| Маршрут | База `6593e3e` | Сейчас |
|---|---|---|
| `POST /v1/decide` | 200, 401 | 200, 401 — без изменений |
| `GET /v1/decisions` | 200, 401 | 200, 401, **422** |
| `GET /v1/profiles/{id}` | 200, 401, 404 | 200, 401, 404 — без изменений |

**Что было неверно.** Первая версия отчёта утверждала, что оба появившихся `422` — «реально существующие ответы, которые рукописный документ не описывал», и ссылалась на эмпирическую проверку. Для `/v1/profiles/{id}` это **круговой аргумент**: реализация добавила параметру пути `max_length=64`, которого раньше не было, и проверка гонялась уже по изменённому коду. До этой задачи id из 65 символов давал `404`; ограничение превращало его в `422`. То есть коммит не обнаружил ответ, а **создал** его. То же касалось `max_length` на query-параметрах `session_id` и `model`.

**Что сделано.** Три необъявленных ограничения сняты — задача 8 обязана приводить документ к сервису, а не менять сервис. Правило самой задачи («расходятся — значит неверна модель») здесь работает против ограничений: старый контракт `422` у профилей не описывал. `alias="id"` оставлен: он, наоборот, приводит приложение к контракту, где путь всегда назывался `{id}`, а маршрут звался `{profile_id}` — настоящее расхождение, которое генерация вскрыла.

После снятия ограничений `422` у `/v1/profiles/{id}` стал недостижимой автоматикой FastAPI (документируется для любого маршрута с параметром) и отсекается в `api/openapi.py`. Поведение проверено: id из 200 символов → `404`, длинный `session_id` → `200`.

**`422` у `/v1/decisions` — настоящий и предшествует задаче.** `limit` нёс `ge=1, le=500` и до неё; рукописный документ ответ не описывал. Закреплён тестом `test_decisions_rejects_a_limit_outside_its_bounds`.

### 3. `openapi.yaml`: схемы

**Тоже переписано после ревью: прежняя формулировка «остальной состав схем не изменился» неверна.** Изменения есть, все — в сторону точности, и все видимы кодогенератору клиента:

| Схема | Что изменилось | Почему |
|---|---|---|
| `DecisionRecord` | **добавлено поле `model_raw_response`** | Поле есть на модели и уже возвращалось из `/v1/decisions`; рукописный документ его опускал. Стоит внимания владельца: контракт теперь публично объявляет, что лента отдаёт сырой вывод модели ступени 2 |
| `DecisionRecord` | `required` 0 → 24 | Модель действительно требует все 24; документ утверждал, что ничего не обязательно |
| `Error` | `required` 0 → 1 | То же |
| `DecisionRecord`, `DecisionListResponse`, `Error` | убрано `additionalProperties: true` | Отсутствие ключа в JSON Schema означает то же самое; для кодогенерации видно |
| ответы целиком | `default: null` 9 → 4 | FastAPI рендерит response-модели в режиме сериализации, где значения по умолчанию не выводятся |
| — | добавлены `HTTPValidationError`, `ValidationError` | Тело настоящего `422` у `/v1/decisions` |
| `DecisionView` → `DecisionRecord` | переименование | Следование правилу задачи: в закоммиченном контракте схема называлась `DecisionRecord` |

Ни одна схема не потеряна.

### 4. Отметки `provisional`

`grep -c provisional contracts/openapi.yaml` → **0**. Замечание из `contracts/README.md` («генератор помечает реализованные эндпоинты как provisional») закрыто.

## Процессное условие

`contracts/` меняется только PR-ом с упоминанием всех трёх направлений (`contracts/README.md`). Работа сделана и закоммичена; **решение о мердже — владельца продукта**, и этот раздел — то, что нужно прочитать для решения. Сводка изменения контракта, коротко и полностью:

1. Добавлены описания полей и маршрутов. На поведение не влияют; обе JSON-схемы без `description` побайтово идентичны прежним.
2. `GET /v1/decisions` получил документированный `422` — ответ существовал и до задачи, документ его не описывал. Закреплён тестом.
3. `DecisionRecord` получил поле `model_raw_response`, которое лента и так возвращала. **Требует внимания:** контракт теперь публично объявляет, что в ленте лежит сырой вывод модели ступени 2.
4. Три схемы обзавелись списками `required` и потеряли `additionalProperties: true`; пять `default: null` исчезли. Всё это приведение документа к моделям, но кодогенератору клиента видно.
5. `DecisionView` переименована в `DecisionRecord` — так схема называлась в уже закоммиченном контракте.

Ни одного поля не удалено, ни один тип не изменён, `POST /v1/decide` сохраняет свойство «всегда 200, кроме 401». Изменений поведения сервиса нет: три ограничения параметров, которые задача успела добавить, сняты (см. раздел 2).

## Что осталось незакрытым

- Отчёт субагента отсутствует: он упал до его написания. Настоящий документ его заменяет, но доказательства TDD за реализацию (красный тест до кода) утрачены — их некому предъявить. Тесты, которые он написал, проверены контроллером и проходят, но порядок их появления не подтверждён.
- Замечание из ревью задачи 6 — экспортёр вручную описывал `DecisionListResponse` и `Health` под комментарием «эти маршруты возвращают обычные словари», что перестало быть правдой — закрыто этой задачей: обе схемы теперь порождаются из моделей.
