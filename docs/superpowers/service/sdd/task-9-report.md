## Concerns

- **Idempotency key surfaced by the coordinator, not implemented (correctly out of scope for this task).** The adapter contract (post-dates this brief) assumes idempotency by `(harness, session id, call id, direction)`. `DecisionRow` currently has no `call_id`/`direction` columns and no unique constraint expressing that tuple. Adding it later is *not* blocked by anything here — it is a straightforward additive migration (new nullable columns + a new unique index, `0002_...`). The one thing worth flagging: `DecisionRepo.insert()` currently does a plain `session.add()` + `commit()` with no `ON CONFLICT` handling (unlike `SessionRepo.upsert`/`cache_put`, which do use `pg_insert(...).on_conflict_do_update`). If a future idempotency key is added as a unique constraint, a naive repeat `insert()` call will raise `IntegrityError` instead of being silently absorbed — whoever implements idempotency will need to either catch that at the call site or change `insert()` to an upsert/`on_conflict_do_nothing`. Nothing to act on now; noting it because it is exactly the kind of downstream friction the coordinator asked about.
- **`service/docker-compose.yml` was written but not exercised via `docker compose up`.** The task described a Postgres 16 container already running on port 5433 with matching credentials, so I connected to that instance directly (via `asyncpg`) rather than starting a second one that would conflict on the same host port. The compose file's shape matches the brief exactly; I did not verify `docker compose up -d db` end-to-end myself. If the existing container's config ever diverges from this compose file, that divergence would go undetected until Task 12 actually runs it.
- **`agentgate` database (alembic.ini's default target) had to be created by hand** — it did not pre-exist alongside `agentgate_test`. I created it directly via `asyncpg` (`CREATE DATABASE agentgate`) so `alembic upgrade head` had something to run against for verification purposes. This is not part of the application's normal startup path (Task 11 presumably handles that, or it's an ops concern), just noting it since it was a step I had to take that isn't in the brief.

**Fix 1 — `limit` unvalidated.** `DecisionRepo.list` now does `limit = max(1, min(limit, 1000))` before building the query. `limit=0`/negative no longer silently return nothing (or, for negative values, raise a `DBAPIError` wrapping `asyncpg.InvalidRowCountInLimitClauseError` — verified that was the pre-fix crash shape by running `limit=-1` manually before writing the fix); a pathologically large `limit` no longer passes straight through as an unbounded read. Documented in the method's docstring.

**Fix 2 — naive `expires_at` silently reinterpreted.** `SessionRepo.cache_put` now raises `ValueError` up front if `expires_at.tzinfo is None`, with a docstring explaining why: a naive value is not treated as UTC by the driver — it is reinterpreted through the connection's session timezone — while `cache_load_valid`'s `now` is always tz-aware UTC, so a naive input would silently shift when the entry expires (the review's own repro: a naive `datetime(2099,1,1,12,0,0)` on an MSK host round-tripped through Postgres as `09:00:00+00`, three hours early).

### Important 3 — FK ordering: docstrings + tests

Added to `DecisionRepo`'s class docstring and `insert`'s docstring: `session_id`, when not `None`, is a foreign key to `sessions.id`, and the referenced session must already exist — `SessionRepo.upsert` before `DecisionRepo.insert`. Added the parallel note to `SessionRepo.cache_put`'s docstring for its two FKs (`decisions.id`, `sessions.id`).

Two new tests pin the failure shape:
- `test_insert_orphan_decision_raises_integrity_error` — no session ever upserted, `DecisionRepo.insert` with `session_id="does-not-exist"` raises `IntegrityError`.
- `test_cache_put_orphan_decision_raises_integrity_error` — a real session exists but no decision does; `cache_put` with a bogus `decision_id` raises `IntegrityError`.

These were already-correct behavior (Postgres enforces the FK regardless of what the ORM code does), so both passed on first run — not a bug fix, a regression guard plus documentation of a real ordering requirement that Task 10 must observe.

### Important 4 — `agentgate_test` (not `agentgate`) is the real fresh-checkout gap; fixed in the compose file

Correcting my own earlier disclosure: the reviewer is right and I had it backwards. `alembic.ini` targets `agentgate`, which `POSTGRES_DB: agentgate` in `docker-compose.yml` already creates — nothing was missing there. The actual gap is `agentgate_test`, the database `AGENTGATE_TEST_DB_URL` points at for the store test suite: on a clean checkout, `docker compose up -d db` alone never creates it, so pointing the documented URL at a fresh container makes `tests/test_store.py` **error on connection** rather than skip — worse than either passing or skipping cleanly, because it looks like a bug report instead of a missing-database report.

**Fixed in the compose file**, not the README alone (I did both — see below): added `service/scripts/init-test-db.sql` (`CREATE DATABASE agentgate_test;`) mounted read-only into `/docker-entrypoint-initdb.d/init-test-db.sql` in `service/docker-compose.yml`. Postgres's entrypoint runs every `*.sql`/`*.sh` file under that directory exactly once, on first startup of an empty data directory — no extra step needed on a clean `docker compose up -d db`.

**Chose the compose-file fix over a README-only note** because a README instruction is something a human has to remember and type; the init script makes the correct state the automatic one. I also added a short section to `service/README.md` documenting the mechanism and its one real limitation: init scripts only run against an *empty* data directory, so a pre-existing `pgdata` volume from before this change (or one seeded a different way, like the container this task ran against, which was started directly with `POSTGRES_DB=agentgate_test` rather than through this compose file) will not retroactively gain `agentgate_test` — the README gives the two remedies (`docker compose down -v` to reset the volume, or a manual `CREATE DATABASE`).

**Verified end-to-end**, not just read for plausibility: ran a disposable `postgres:16-alpine` container on a scratch port (`docker run ... -p 15433:5432 -v .../init-test-db.sql:/docker-entrypoint-initdb.d/init-test-db.sql:ro`, no pre-existing volume), waited for `pg_isready`, then `psql -c "select datname from pg_database"` — `agentgate_test` was present alongside `agentgate` with zero manual steps. Also ran `docker compose config` against the edited `docker-compose.yml` to confirm it parses and the new bind mount resolves to the right path. The disposable container was stopped and removed (`docker stop`, `--rm`) after the check; the pre-existing live container this task's tests run against was never touched.
