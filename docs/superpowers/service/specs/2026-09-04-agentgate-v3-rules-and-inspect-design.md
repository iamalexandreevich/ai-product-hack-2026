# AgentGate v3 — правила пользователя и проверка результатов

Дата: 4 сентября 2026. Статус: согласовано в brainstorming, ждёт плана реализации.

Этот документ детализирует v3 из `context-versions-roadmap.md` и отвечает на предложение направления адаптеров (`inspect-openapi.yaml`, «PostToolUse inspection and the deterministic ruleset»). Он включает v2 (`2026-09-04-agentgate-v2-design.md`) и заменяет черновик `v3-tool-result-evaluation.md` там, где они расходятся. Маскирование инъекций, которое роадмап относил к v4, здесь в детерминированной форме: адаптеры уже ждут вердикт `mask`, а без него `/v1/inspect` нечего отдавать.

---

## 1. Что добавляется и зачем

Две вещи, обе — ответ на то, что адаптеры уже шлют или уже ждут:

1. **`rules` в `DecideRequest`** — детерминированная политика пользователя: уровень, выбранный при установке, и списки `allow` / `ask` / `deny`, которые он правит руками. Сегодня поле принимается и игнорируется; после v3 оно участвует в ступени 1.
2. **`POST /v1/inspect`** — второй шов: оценка *результата* инструмента до того, как он попадёт в контекст модели. Инъекция в README читается агентом как инструкция, и классификатор действий её не закрывает: он смотрит на уже отравленный контекст. Адаптеры зовут этот маршрут с первого дня, получают 404 и пропускают результат как есть.

## 2. Решения, принятые в brainstorming

| Вопрос | Решение | Почему |
|---|---|---|
| Приоритет правил пользователя | hard-deny → `rules.deny` → запреты профиля → `rules.ask` → `rules.allow` → серверный allowlist → ступень 2 | Клиент может ужесточить и разрешить серое, но не может разрешить то, что запрещает оператор или hard-deny |
| По чему матчить шаблоны | Канонический вид из `NormalizedAction`, не сырая строка | Правило «решение по сырой строке запрещено» остаётся; `$X -rf` не обходит |
| Объём inspect | Ступень 1 детерминированная + ступень 2 по флагу профиля, только когда ступень 1 что-то нашла | Классификатор на каждый результат — секунда и деньги; адаптеры сами отговаривают |
| Режим отказа inspect | Ступень 2 при ошибке откатывается к вердикту ступени 1; невалидное тело — `drop` | Спросить человека некого; сервис всегда отвечает содержательно и никогда 500 |
| Лимит `output` | 256 КБ, проверяется целиком | Усечение пропускает инъекцию в хвосте; детерминированная ступень это тянет |
| Хранение | Одна таблица и одна лента с полем `kind` | Сессия читается как пары `out`/`in` по `call_id`, без второго формата |

## 3. `rules` в `DecideRequest`

### 3.1. Контракт

```json
"rules": {"version": 1, "level": "medium",
          "allow": ["git status", "git diff*", "npm test*"],
          "ask":   ["npm install*", "git push*", "curl *"],
          "deny":  ["sudo *", "curl * | sh", "**/.env", "~/.ssh/**"]}
```

| Поле | Тип | Смысл |
|---|---|---|
| `version` | int | Только `1`. Другое → `ask`, `api.unsupported-rules` |
| `level` | string ≤ 32 | `low`, `medium`, `high`, `custom`. Информационно, пишется в запись |
| `allow`, `ask`, `deny` | string[] | Шаблоны, каждый ≤ 200 символов; суммарно ≤ 500 шаблонов и ≤ 16 КБ, сверх → `ask`, `api.rules-too-large` |

Поле необязательное; отсутствие — поведение как сегодня. Сами шаблоны в запись не пишутся: пишутся `rules_level` и `rules_digest` (sha256 канонического набора), чтобы бенчмарк различал прогоны.

### 3.2. Виды шаблонов

Вид определяется формой, отдельного поля типа нет:

- **путевой** — содержит `/` или начинается с `~` (`**/.env`, `~/.ssh/**`): `fnmatch` по каждому нормализованному пути действия любого инструмента; для `shell` — по путям, извлечённым из AST;
- **командный** — всё остальное (`git diff*`, `curl * | sh`): `fnmatch` по каноническому виду из `NormalizedAction`.

Канонический вид: одна простая команда — argv через пробел; пайплайн — команды через ` | `; составная команда (`&&`, `;`) — каждая часть отдельно. Сырая строка `raw` не участвует нигде.

### 3.3. Правило ступени 1

`rules/client_rules.py`, класс `ClientRulesRule(mode)`, три экземпляра в `STAGE1` на трёх позициях по принятому порядку: `client.deny` сразу после hard-deny, `client.ask` после `profile.*`, `client.allow` перед `allowlist.*`. Один класс, три `rule_id`, порядок остаётся одним списком.

Составная команда: `deny` и `ask` срабатывают, если подходит хоть одна часть; `allow` — только если каждая часть подходит под какой-нибудь `allow`-шаблон и в команде нет `eval`, подстановок и редиректов в файлы — те же условия, что у серверного allowlist.

`Rule.evaluate(action, policy)` не меняется: правила привязываются к `Policy` при разборе запроса, как workspace — `Policy.bind(profile, workspace, client_rules)`. Ступень 1 по-прежнему видит только действие и политику. `reason` при `client.deny` — «blocked by your rules», без шаблона: `reason` уходит модели.

Тип `ClientRules` в `domain/client_rules.py`: разбор на путевые и командные, канонизация, `digest`.

## 4. `POST /v1/inspect`

### 4.1. Запрос `InspectRequest`

Форма адаптеров как есть, с уточнениями:

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `session_id`, `harness`, `profile_id`, `metadata` | как в `decide` | | |
| `call_id` | string ≤ 128 | да | Связывает с `decide` того же вызова |
| `tool` | enum | да | Как в `decide` |
| `tool_name` | string ≤ 64 | да | Имя инструмента харнесса |
| `status` | `completed \| error` | да | Текст ошибки — тоже недоверенный |
| `output` | string ≤ 262 144 байт | да | Сверх → `drop`, `api.output-too-large` |
| `provenance` | объект по `kind` | да | `file{path}`, `shell{command}`, `web{url}`, `mcp{server,tool}`, `subagent{session_id}`, `unknown` |
| `args` | `ActionArgs` | да | Аргументы вызова, породившего результат |
| `user_request` | string | да | Пустой → последний `human/human` ход истории |
| `history`, `protocol` | как в `decide` | нет | Те же `Turn` и лимиты |

`call_id` добавляется и в `DecideRequest` как необязательное поле, чтобы пара `out`/`in` читалась в ленте без `metadata`.

### 4.2. Ответ `InspectResponse`

`verdict: pass | mask | drop`; `output` — только при `mask`, обязателен и авторитетен, адаптер подставляет его дословно; `reason`, `suggest`, `stage`, `rule_id`, `model`, `latency_ms`, `cached`, `decision_id`, `protocol`. Всегда HTTP 200; `401` — единственное исключение.

### 4.3. Заголовок `Idempotency-Key`

Та же семантика и то же хранилище повторов, что у `decide`: личность — дайджест `InspectRequest` без `metadata`. Адаптеры уже строят ключ с `direction: in`.

### 4.4. Отказы

Все HTTP 200. Инвариант «`allow` по ошибке недостижим» получает пару: **`pass` по ошибке недостижим**.

| Случай | Ответ |
|---|---|
| невалидное тело | `drop`, `api.invalid-request` |
| `output` сверх лимита | `drop`, `api.output-too-large` |
| исключение в детекторе или кэше | `drop`, `api.internal-error`; никогда 500 |
| ошибка ступени 2 | вердикт ступени 1 как есть, `error` в записи |
| недоступность сервиса | политика адаптера (fail-open у них осознанный), сервис её не переопределяет; фиксируется в `contracts/README.md` |

## 5. Каскад inspect

```
запрос → валидация → повтор по Idempotency-Key? → кэш по содержимому? → ступень 1 (детекторы) →
ступень 2 по флагу, только если ступень 1 что-то нашла → ответ → запись
```

### 5.1. Ступень 1 — детекторы

По строкам `output`, таблица в `inspect/detectors.py` — единственный источник знания «что похоже на инъекцию», шаблоны на английском и русском:

| `rule_id` | Что ловит | Действие |
|---|---|---|
| `inspect.injection` | императивы к модели: `ignore/disregard (all) previous instructions`, `you are now in … mode`, `do not mention this to the user`, `system:`/`assistant:` в начале строки, HTML-комментарии с инструкциями | строка заменяется |
| `inspect.pipe-exec` | `curl\|wget … \| sh\|bash` в тексте и в fenced-блоках | строка заменяется |
| `inspect.encoded` | base64-подобная последовательность длиннее 512 символов | строка заменяется |
| `inspect.invisible` | zero-width, bidi-override и прочие управляющие символы Unicode вне обычного текста | строка очищается, не удаляется |

### 5.2. Вердикт ступени 1

Ничего не помечено — `pass`. Помечены строки — `mask`: каждая помеченная строка заменяется на `[gate: instruction-like text removed]`, `reason` называет число строк. Помечено больше половины строк, или весь `output` — один base64-блоб, — `drop`. Пороги — константы модуля `inspect/mask.py`, не профиль.

### 5.3. Ступень 2 — по флагу

Профиль: `inspect: {classifier: off | on-flag}`, умолчание `off`. При `on-flag` классификатор зовётся только когда ступень 1 что-то нашла. Ответ по закрытой схеме `P | M | D` с `reason`: может смягчить `mask` до `pass` (ложное срабатывание) или ужесточить до `drop`, но не может отменить `inspect.invisible`. Промпт — закрытый список: профиль, `[TASK]`, `[HISTORY]`, `[PROVENANCE]`, `[FLAGS]` со сработавшими детекторами, `[OUTPUT]` в экранированном виде. Любая ошибка — вердикт ступени 1, `error` в записи. Отдельный протокол `InspectClassifier` по образцу `Classifier`.

### 5.4. Провенанс

В этом раунде не меняет пороги: идёт в запись и в промпт ступени 2. Пороги по источникам — после того, как лента покажет ложные срабатывания.

### 5.5. Кэш по содержимому

Ключ `sha256(output)` в рамках `profile_hash` и `kind` провенанса, TTL сессии. Кэшируются все три вердикта: результат детерминирован по содержимому, в отличие от `deny` в `decide`, который зависит от контекста сессии. Ответ из кэша — `cached: true`, `stage: 0`. Протокол `InspectCache` (`get`, `put`) с in-memory реализацией; восстановление из Postgres не делается — промах стоит одной детерминированной проверки.

## 6. Хранение и устройство кода

**Таблица.** `decisions` получает `kind: decide | inspect` (умолчание `decide`), `call_id`, `provenance` JSONB, `replacement` (текст `mask`, иначе `null`), `rules_level`, `rules_digest`. Для inspect-строк `decision` хранит `pass | mask | drop`, `raw` — `output`, `normalized` — `{tool_name, status, provenance}`. Миграция `0004`. `DecisionRecord` получает те же поля как необязательные, `decision` — объединение двух enum. JSONL пишет ту же запись. `GET /v1/decisions` получает фильтр `?kind=`.

**Пакет `agentgate/inspect/`**, зеркально `rules/` и `classify/`: `detectors.py`, `chain.py` (`INSPECT_STAGE1`), `mask.py`, `classify.py`.

**`engine/inspector.py`** — `Inspector.inspect(request) -> Inspection`: кэш → ступень 1 → ступень 2 по флагу → откат. `Inspection` — исход целиком с `to_response()` и `to_record()`, как `Decision`. `Gate` не меняется. `bootstrap.build_service` собирает `Inspector` рядом с `Gate`, `Service.inspector`.

**`rules`**: `rules/client_rules.py` и `domain/client_rules.py`; `Policy.bind` получает необязательный `client_rules`.

## 7. Тесты

- `domain/test_client_rules.py`: разбор путевых и командных шаблонов, канонизация argv и пайплайнов, дайджест.
- `rules/test_client_rules.py`, табличные: `git diff*` разрешает `git diff HEAD`, не `git push`; `curl * | sh` ловит пайплайн из AST и `$X | sh` через переменную; `**/.env` ловит путь любого инструмента; составная команда по `allow` только целиком; приоритет: `client.allow` не бьёт `hard-deny` и `profile.path`, `client.deny` бьёт серверный allowlist.
- `inspect/test_detectors.py`: таблица инъекций на двух языках, обфускация регистром и пробелами, отсутствие ложных срабатываний на обычном README и логе сборки.
- `inspect/test_mask.py`: замена строк, порог `drop`, очистка невидимых символов, `replacement` не содержит помеченного текста.
- `engine/test_inspector.py`: кэш по содержимому и профилю; классификатор не зовётся при `off` и при чистой ступени 1; смягчение `mask` → `pass`; откат при ошибке; `inspect.invisible` не смягчается; на каждый путь отказа — `pass` недостижим.
- `api/test_app.py`: оба эндпоинта, `Idempotency-Key` для inspect, `?kind=`, `call_id` в `decide`, три отказа `rules`.
- Latency: детекторы на 256 КБ p50 ≤ 20 мс — отдельный бюджет; бюджет ступени 1 `decide` ≤ 1 мс сохраняется с `rules` из 500 шаблонов.
- Контракты перегенерированы; `contracts/README.md` описывает оба эндпоинта и `rules`.

## 8. Порядок реализации

Сначала `rules` (домен, правило, привязка к политике, контракт и запись), потом `inspect` (контракт, детекторы, mask, кэш, inspector, классификатор, API и bootstrap, хранение), затем документация и отчёт. Волнами по графу зависимостей, как v2.

## 9. Не входит

- Пороги детекторов по провенансу.
- Taint результата в счётчики сессии и provenance-правило в `decide`.
- Классификатор на каждый результат.
- `POST /v1/decide:batch`, версия харнесса.
- Хэш `rules` вместо тела.
- Семантическая защита от перефразированных инъекций (v4 в полном объёме).
