# Авто-деплой на сервер

Дата: 3 сентября 2026. Статус: требование владельца продукта. Реализуется как задача деплоя после Task 12 (Docker) — она даёт `Dockerfile` и `docker-compose.yml`, на которые деплой опирается.

## Цель

Одна команда с локальной машины выкатывает сервис на VDS напрямую: `make deploy`.

## Целевой сервер

Реквизиты уже существуют в `service/.env` (не в гите, покрыт `service/.gitignore`): `VDS_IP`, `VDS_LOGIN`, `VDS_PASSWORD`. Деплой читает их оттуда и **никогда** не хардкодит и не коммитит.

## Форма: Makefile поверх docker compose по SSH

`service/Makefile` с целями:

```
make build     — docker build локально (или на сервере, см. ниже)
make deploy    — выкатить текущий закоммиченный код на сервер
make logs      — docker compose logs -f с сервера
make ps        — статус контейнеров на сервере
make rollback  — откат на предыдущий образ
```

`make deploy` по шагам:
1. проверить, что рабочее дерево чистое (деплоим закоммиченное, не локальные правки);
2. синхронизировать код на сервер (`rsync` каталога `service/`, исключая `.venv/`, `.env`, `logs/`, `__pycache__/`);
3. на сервере: `docker compose up -d --build` — поднять сервис и Postgres из `docker-compose.yml`;
4. применить миграции: `docker compose exec gate alembic upgrade head`;
5. проверить здоровье: `curl -fsS http://localhost:8400/healthz` на сервере, ненулевой код → деплой считается неуспешным.

## Как не класть пароль в команды

Пароль в аргументах `ssh`/`scp` виден в списке процессов и в истории shell. Поэтому:

- **Предпочтительно — SSH-ключ, а не пароль.** `make setup-ssh` один раз копирует локальный публичный ключ на сервер (`ssh-copy-id`), после чего пароль в деплое не участвует вовсе. Это разовое действие и его выполняет человек.
- Пока ключа нет — `sshpass -f <(…)` читает пароль из `.env` через файловый дескриптор, а не из argv. Это компромисс, помеченный в Makefile как временный.

## Секреты на сервере

Провайдерские ключи LLM и `AGENTGATE_TOKEN` (или выданные API-ключи, см. `api-keys.md`) на сервере живут в `.env` рядом с `docker-compose.yml`, который его читает через `env_file`. Локальный `service/.env` на сервер **не копируется** — серверный `.env` заводится один раз вручную, у него другое содержимое (боевые ключи, не VDS-креды).

## Что должен решить владелец продукта до реализации

1. **Root по паролю по SSH — это то, с чем деплоим в проде?** Настоятельно рекомендую перейти на SSH-ключ и невыключенный root-по-паролю закрыть. Пароль в `.env` на машине разработчика — уже поверхность утечки; в CI это будет секрет пайплайна. Решение за владельцем, но по умолчанию спека идёт к ключу.
2. **Сборка образа — локально с пушем в реестр, или `--build` на сервере?** На сервере проще (не нужен реестр), но занимает CPU сервера и требует там исходников. Для хакатона — `--build` на сервере; для продакшена — реестр.
3. **CI или только локальный `make deploy`?** Требование сформулировано как «напрямую на сервер», поэтому базовая форма — локальный Makefile. Если нужен деплой по push в ветку — это отдельный слой (GitHub Actions с секретами), добавляемый поверх тех же целей Makefile.
4. **Один сервер или staging + prod?** Влияет на то, параметризовать ли цель (`make deploy ENV=prod`).

**Сервер.** `109.172.95.51`, Ubuntu 26.04, 3.9 ГБ RAM, 59 ГБ диска (занято 10%), Docker 29.7.2, Compose v5.5.0. Каталог развёртывания `/opt/agentgate` — копия дерева `service/`, не git-репозиторий.

**Доступ.** Заведён отдельный деплой-ключ `~/.ssh/agentgate_deploy` **без парольной фразы** и установлен в `authorized_keys` root. Причина: личный `id_ed25519` защищён фразой, а агент пуст, поэтому неинтерактивно им пользоваться нельзя. Пароль из `.env` в деплое больше не участвует. `ssh-copy-id` при этом дважды зависал — ключ поставлен дописыванием в `authorized_keys` через одну парольную сессию; Makefile должен делать так же, а не звать `ssh-copy-id`.

**Политика перезапуска.** У обоих сервисов было `restart: no` — то есть после перезагрузки сервера или падения контейнера сервис не поднимался сам. Проставлено `unless-stopped`. Резервная копия исходного compose — `/opt/agentgate/docker-compose.yml.bak`.

**Диагноз прошлой остановки.** Контейнер `gate` вышел с кодом 137, что похоже на OOM, но `OOMKilled=false`, а база вышла с кодом 0 одновременно с ним. Это `docker compose down`, а не падение. До остановки сервис работал: в логах успешные `POST /v1/decide` и живые вызовы OpenRouter.

## Известные препятствия, которые Makefile обязан снять

1. **Имя переменной не совпадает.** `docker-compose.yml` требует `AGENTGATE_TOKEN` и падает без неё с явным сообщением; в локальном `service/.env` переменная называется `TOKEN`. Серверный `.env` в `/opt/agentgate` содержит правильные имена (`AGENTGATE_TOKEN`, `OPENROUTER_API_KEY`), но расхождение локального имени с тем, что требует compose, — ловушка для того, кто попробует поднять сервис у себя.
2. **`/healthz` отдаёт `degraded`, `db: false`.** Сервис поднят, база здорова, но проба соединения не проходит. Не разобрано; деплой не считается успешным, пока `/healthz` не отдаёт `ok`, — это уже записано в шагах `make deploy`.
3. **`rsync` не читает `.gitignore`.** Исключения из спеки (`.venv/`, `.env`, `logs/`, `__pycache__/`) перечислены отдельным списком, который разойдётся с `.gitignore`. Правильный ход — `--filter=':- .gitignore'`: список остаётся один. `service/.dockerignore` заведён отдельно (контекст сборки был 58 МБ, из них 59 — локальный `.venv` с macOS-бинарниками; стал 0.4 МБ), но rsync о нём тоже не знает.

## Открытый вопрос: как версионировать код на сервере

Поставлен владельцем продукта 4 сентября. Сейчас `/opt/agentgate` — не git-репозиторий, а результат `rsync`, поэтому по нему нельзя ответить, какая ревизия развёрнута. Обнаружено следствие: на сервере лежит `Makefile`, которого нет в репозитории, — он приехал из другой ветки, и восстановить, из какой, невозможно.

Осложняющее обстоятельство: репозиторий монорепа на три независимых направления (`service/`, `adapters/`, `benchmark/`), и деплой касается только одного. Варианты, между которыми нужно выбрать:

- **Метка ревизии в образе.** `docker build --build-arg GIT_SHA=$(git rev-parse HEAD)`, отдавать её из `/healthz` или `/v1/version`. Дёшево, отвечает на «что развёрнуто», но не даёт откатиться на произвольную ревизию.
- **Git на сервере.** `/opt/agentgate` становится клоном, деплой — `fetch` + `checkout <sha>`. Отвечает и на «что развёрнуто», и на «откатись», но тянет весь монорепозиторий ради одной папки (лечится sparse-checkout).
- **Реестр образов.** Тег образа = ревизия, откат = запуск прежнего тега. Самое чистое для прода, требует реестра.

Для хакатона достаточно первого. Решение за владельцем; до него `make rollback` из списка целей опирается на `.previous_gate_image`, что откатывает ровно на один шаг и не знает, какой ревизии этот шаг соответствует.

## Границы

- Деплой — outward-facing действие с необратимыми последствиями на чужой машине. Автоматизировать команду можно; **запускать её без явного согласия владельца — нельзя.** `make deploy` выполняет человек.
- Ротацию `VDS_PASSWORD` (он лежал незашифрованным в `.env`) стоит сделать независимо от этой задачи — если пароль где-то светился, его надо сменить на сервере.

## Наследуемые ограничения

- Fail-closed относится к решениям сервиса, не к деплою; но health-check после деплоя обязателен — сервис, не поднявшийся на `/healthz`, считается неуспешным деплоем и должен откатываться, а не оставаться в полурабочем состоянии.
- Только Postgres; `docker-compose.yml` поднимает его как зависимость сервиса.
