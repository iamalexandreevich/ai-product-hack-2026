# AgentGate — дорожная карта версий (v1 → v5)

Дата: 3 сентября 2026. Статус: **принято владельцем продукта, порядок зафиксирован.**

Основная ось развития: сколько контекста агента сервис видит и берётся оценивать. По ней идут v1→v4, и каждая включает предыдущую.

**v5 стоит на другой оси** — независимость от провайдера модели. Она ортогональна первой: её можно делать до, после или параллельно любой из v2–v4, и она ничего не меняет в объёме контекста. Номер даёт владелец продукта, чтобы вещь не потерялась; порядковой зависимости от v4 у неё нет.

| Версия | Что видит сервис | Спека | Статус |
|---|---|---|---|
| **v1** | последний tool-call + последнее сообщение пользователя | `2026-09-03-agentgate-v1-design.md` | **реализуется** |
| **v2** | v1 + предшествующий диалог: `assistant` + `toolcall` + `toolresult` + `human` | `v2-dialogue-context.md` | спроектировать |
| **v3** | v2 + оценка самих `tool-result` | `v3-tool-result-evaluation.md` | спроектировать |
| **v4** | v3 + Context Guard: маскирование промпт-инъекций внутри `tool-result` | `v4-context-guard.md` | спроектировать |
| **v5** | *(другая ось)* самохостед-модель как полноценный провайдер ступени 2 | `v5-self-hosted-models.md` | спроектировать |

## Где мы сейчас: v1, подтверждено кодом

- `DecideRequest` (`service/agentgate/api/schemas.py`) несёт `tool`, `raw`, `args`, `user_request`. Полей под историю нет.
- `build_user_message` (`service/agentgate/stage2/prompt.py`) рендерит `[TASK]`, `[ACTION]`, `[FLAGS]`, `[STAGE1]`.
- Закрытый список содержимого промпта истории не содержит.

Граница v1 задана спекой сознательно, а не является недоделкой.

## v5 — самохостед-модель как полноценный провайдер

**Цель:** ступень 2 работает на модели, которую разворачивает сам оператор (vLLM, llama.cpp, Ollama, TGI), без облачного провайдера в контуре. Мотив — данные о действиях агента и содержимое `[TASK]` не покидают периметр, и стоимость решения перестаёт зависеть от внешнего тарифа.

### Что уже работает и переделывать не нужно

Проверено по коду на 4 сентября 2026:

- `base_url` задаётся в конфигурации модели профиля — облако и локальный сервер различаются одной строкой YAML.
- `api_key_env: null` корректно обрабатывается: клиент **не** ставит заголовок `authorization`, поэтому сервер без аутентификации работает из коробки.
- `structured_output: false` убирает `response_format` из запроса, а `_strip_fences` разбирает ответ, обёрнутый в markdown-ограждение. То есть сервер, не умеющий JSON-schema, уже не блокер.
- В `profiles/default-dev.yaml` запись `local` (`http://localhost:8000/v1`, `qwen3.5-4b`) существует.

Иначе говоря, «подключить локальную модель» — это уже конфигурация, а не разработка. v5 не про это.

### Чего на самом деле нет

1. **`/healthz` никогда не проверяет модель.** Поле `llm` захардкожено в `null` (`api/app.py`). Для облачного провайдера это терпимо; для сервера, который оператор держит сам, это разница между «шлюз здоров» и «шлюз здоров, но каждое решение молча деградирует в `ask`, потому что модель не отвечает». Это первое, что нужно сделать, и это самый дешёвый пункт списка.
2. **Нет согласования возможностей.** `structured_output` — статический флаг в YAML: оператор обязан заранее знать, умеет ли его сборка `response_format: json_schema`. vLLM, llama.cpp и Ollama реализуют это по-разному и по-разному ломаются. Нужна либо проба при старте, либо деградация по первому отказу с записью в лог.
3. **Нет запасного пути.** Реестр моделей статичен на профиль: если локальный сервер лёг, все решения идут в `ask` до вмешательства человека. Нужна политика «локальная модель, при отказе — облачная» или явное решение, что fail-closed здесь и есть желаемое поведение.
4. **Нет проверенного пути и документации.** Ни одного теста против настоящего локального сервера, ни инструкции по запуску. `timeout_ms: 1500` у записи `local` взят с потолка и почти наверняка мал для холодной модели.

### Границы

- Ступень 1 не затрагивается: она детерминированная и модели не видит.
- Закрытый список содержимого промпта не меняется. Смена провайдера не даёт повода что-то в промпт добавить.
- Fail-closed сохраняется: недоступная локальная модель — это `ask`, а не `allow`.

## Принятое решение по порядку

Порядок версий — решение владельца продукта и не пересматривается. Из него следует зафиксированное окно уязвимости, которое здесь записано, чтобы о нём не забыли, а не чтобы оспорить порядок:

**с v2 подконтрольный атакующему вывод инструментов попадает в контекст, а Context Guard приезжает на v4.** Две версии этот текст живёт в промпте без семантической защиты.

Смягчение, которое не меняет порядок и обязательно к исполнению на v2 — см. `v2-dialogue-context.md`, раздел «Экранирование ≠ Context Guard»:

- **Экранирование** (v2, обязательно) защищает *целостность формата*: `tool-result` не может подделать секцию промпта переводом строки. Механика уже написана и проверена в Task 7.
- **Context Guard** (v4) защищает *семантику*: текст вида «игнорируй предыдущие инструкции» перестаёт читаться моделью как инструкция.

Это разные задачи. Экранирование на v2 — базовая гигиена формата, а не досрочный Context Guard.

## Сквозные требования ко всем версиям

Наследуются из v1 и не ослабляются:

- Fail-closed: любая ошибка, таймаут, невалидный ответ → `ask` с HTTP 200. `allow` по ошибке невозможен.
- Решение по сырой строке команды запрещено; только по `NormalizedAction`.
- Hard-deny не переопределяется ничем и не заменяется на `ask` эскалацией.
- Решение трёхзначное: `allow | deny | ask`. Hard-deny требует уверенности; когда цель действия неопределима, честный ответ — `ask`, а не отказ и не молчание.
- `deny` и `ask` не кэшируются; кэшируется только `allow`.
- Бюджет: p50 нормализации + ступени 1 ≤ 1 мс.
- Ретраев к LLM нет: один вызов, один таймаут.
