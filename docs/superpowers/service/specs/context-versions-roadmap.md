# AgentGate — версии по объёму контекста (v1 → v4)

Дата: 3 сентября 2026. Статус: принято владельцем продукта.

Ось развития: **сколько контекста агента сервис видит и берётся оценивать.** Каждая версия включает предыдущую.

| Версия | Что видит сервис | Статус |
|---|---|---|
| **v1** | последний tool-call + последнее сообщение пользователя | **реализуется сейчас** |
| **v2** | v1 + предшествующий диалог: `assistant` + `toolcall` + `toolresult` + `human` | не начата |
| **v3** | v2 + оценка самих `tool-result` (судим результаты, а не только намерения) | не начата |
| **v4** | v3 + Context Guard: маскирование промпт-инъекций внутри `tool-result` | не начата |

---

## Где мы сейчас: v1, подтверждено кодом

- `DecideRequest` (`service/agentgate/api/schemas.py`) несёт `tool`, `raw`, `args`, `user_request` — одно действие и последнюю реплику. Поля под историю нет ни одного.
- `build_user_message` (`service/agentgate/stage2/prompt.py`) рендерит `[TASK]`, `[ACTION]`, `[FLAGS]`, `[STAGE1]`. Истории нет.
- Глобальное ограничение плана перечисляет содержимое промпта закрытым списком, и этот список не содержит диалога.

Это не недоделка, а сознательная граница v1 из спеки: «v1 оценивает одно действие плюс последний запрос пользователя; история, PostToolUse, provenance — roadmap».

## Насколько легко адаптироваться

Форма конвейера — `normalize → ступень 1 → ступень 2`, где единственная валюта решения это `NormalizedAction`, — под расширение контекста подходит хорошо. Добавление истории аддитивно: новое поле в схеме запроса и новая секция в построителе промпта. Переписывать ядро не придётся.

Но есть четыре места, где расширение упрётся, и их лучше знать заранее.

### 1. Закрытый список содержимого промпта — это тест, а не пожелание

Сейчас действует жёсткое правило: в промпт ступени 2 попадают только системный промпт, профиль, prose-слоты, `[TASK]`, `[ACTION]`, `[FLAGS]`, `[STAGE1]`. Оно закреплено тестами и docstring-ами, и Task 7 прошла два раунда ревью, закрывая две рабочие инъекции именно в этой поверхности.

v2 этот список расширяет. Расширять его можно только вместе с той же дисциплиной экранирования: каждое подставляемое значение проходит через `_j()` (`json.dumps`), иначе перевод строки в содержимом подделывает секцию промпта. Механика уже написана и проверена — переиспользовать её, а не изобретать заново.

### 2. Ключ кэша `allow` истории не содержит

```python
allow_cache_key(profile_hash, action_hash, user_request)
```

Под v2 два одинаковых действия с **разной** предшествующей историей дадут один ключ. Разрешение, выданное в безобидном контексте, переиспользуется во враждебном.

Это в точности та коллизия, которую мы убили в Task 4: там два разных тела here-doc давали одинаковый `action_hash`, и закэшированный `allow` для `ls` переигрывался на `rm -rf /`. Лечение то же — дайджест истории входит в ключ. **Сделать это надо в том же коммите, что и v2, а не потом:** пока история не влияет на ключ, кэш работает как механизм закрепления.

### 3. Бюджет усечения

`user_request` режется до 2048 символов с сохранением хвоста. У истории должен быть свой бюджет и своя политика выбрасывания. Важно, что `tool-result` бывают огромными — вывод сборки, дамп таблицы, содержимое файла, — поэтому наивное «берём последние N сообщений» вытеснит из окна и профиль, и само действие.

### 4. v3 меняет семантику решения

`deny` для уже выполненного действия бессмысленен — результат существует. v3 требует других исходов: пометка, taint, влияние на последующие решения сессии. Спека уже относит `/v1/observe`, PostToolUse и provenance к roadmap; v3 это и есть.

## Замечание по порядку: v4 не последняя по важности

По определению v2 уже вносит `toolresult` в контекст. Значит **подконтрольный атакующему вывод инструментов попадает в промпт начиная с v2**, а защита от инъекций в нём приезжает только в v4 — две версии живой уязвимости.

Это ровно тот класс дефекта, который Task 7 закрывала два раунда: текст атакующего внутри промпта, который этот же текст и судит. Отличие в том, что на v2 объём такого текста несопоставимо больше — `tool-result` это вывод команд, содержимое файлов и ответы сети.

Варианта два, и выбор за владельцем продукта:

1. **Внести минимальный Context Guard уже в v2** — экранирование и явную разметку «недоверенные данные» для всего, что пришло из `tool-result`. Полная маскировка инъекций остаётся v4, но базовая неподделываемость формата приезжает вместе с историей.
2. **Осознанно принять риск на v2–v3** и держать эти версии внутренними, не выставляя наружу, пока v4 не готова.

Молчаливый третий вариант — выкатить v2 без экранирования и надеяться — воспроизводит уязвимость, которую мы уже один раз чинили, в большем масштабе.

## Что делать при переходе на v2

- Расширить `DecideRequest` полем истории; ограничить размер как `raw` и `metadata`.
- Провести каждое подставляемое значение истории через `_j()`.
- Добавить дайджест истории в `allow_cache_key` — в том же коммите.
- Задать бюджет усечения и политику выбрасывания, отдельную от `user_request`.
- Обновить закрытый список в docstring `prompt.py` и в `service/CLAUDE.md` — правило «никогда не расширять список, не обновив оба» уже записано там.
