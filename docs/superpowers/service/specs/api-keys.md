# API-ключи: выдача и проверка

Дата: 3 сентября 2026. Статус: требование владельца продукта, спроектировать до Task 11.

## Что есть сейчас

Один статический токен: `Settings.token` из `AGENTGATE_TOKEN`, обязателен при биндинге не на localhost (`validate_token_for_bind()`). Выдачи ключей нет, хранения нет, отзыва нет, различить клиентов невозможно.

## Что требуется

Сервис доступен по API-ключу, и ключи **мы генерируем**. Из этого следуют вещи, которых статический токен не требовал: где ключ рождается, как хранится, как проверяется, как отзывается и как понять, чей он.

## Решения

### Ключ генерируем мы, храним — только хэш

Ключ выдаётся один раз в открытом виде и больше никогда не показывается. В базе лежит хэш.

Это не перестраховка: сервис пишет решения в Postgres и JSONL, база и логи попадают в бэкапы и в руки бенчмарка. Ключ в открытом виде в таблице — это ключ, утёкший вместе с любым дампом.

Хэширование — SHA-256 без соли. Обоснование: ключ генерируем мы сами с высокой энтропией (32 случайных байта), и медленные функции вроде argon2 существуют против перебора **низкоэнтропийных** паролей. Против 256 бит случайности перебор не работает независимо от скорости хэша, а argon2 на горячем пути проверки стоил бы миллисекунды при бюджете сервиса в 1 мс на ступень 1.

Сравнение — `secrets.compare_digest`, никогда `==`. Сравнение хэшей обычным оператором утекает длину совпавшего префикса по времени.

### Формат: префикс плюс секрет

```
agk_<base64url(32 случайных байта)>
```

Префикс `agk_` — не украшение. Он даёт три вещи: ключ опознаётся в логах и дампах глазами; сканеры секретов (gitleaks, GitHub push protection) настраиваются на один паттерн; случайно вставленный не туда ключ видно сразу.

Энтропия — `secrets.token_bytes(32)`, не `random`.

### Генерация — из CLI, не через эндпоинт

```
uv run python -m agentgate keys create --label "kilo-ci" [--expires 90d]
uv run python -m agentgate keys list
uv run python -m agentgate keys revoke <key_id>
```

Эндпоинт для выпуска ключей потребовал бы собственной аутентификации — то есть ключа, чтобы выпускать ключи. Эта задача про начальную загрузку доверия решается либо мастер-ключом (та же проблема этажом выше), либо доступом к машине. Доступ к машине у нас уже есть, значит CLI.

Отдавать ключ только в stdout и никуда не логировать.

### Хранение

Новая таблица `api_keys`, аддитивная миграция `0002_`:

| колонка | смысл |
|---|---|
| `id` | ULID, он же `key_id` для отзыва |
| `key_hash` | SHA-256 от полного ключа, уникальный индекс |
| `label` | человекочитаемая метка: чей это ключ |
| `created_at` | |
| `expires_at` | nullable; NULL — бессрочный |
| `revoked_at` | nullable; отзыв мягкий, строку не удаляем |
| `last_used_at` | nullable, для поиска мёртвых ключей |

Отзыв мягкий, потому что удалённый ключ не отличить от никогда не существовавшего, а при разборе инцидента нужно знать, что ключ был и когда его убрали.

### Проверка на горячем пути

Bearer из заголовка → SHA-256 → поиск по уникальному индексу → проверка `revoked_at is NULL` и `expires_at`. Результат кэшируется в памяти процесса с коротким TTL, иначе каждый `decide` тянет обращение к базе при бюджете в 1 мс.

**Отзыв ограничен временем жизни кэша.** Это осознанный размен, и TTL надо держать коротким (30–60 с). Записать в README: отозванный ключ перестаёт работать не мгновенно.

`last_used_at` пишется **после** ответа, вместе с записью решения — на горячем пути запись в базу недопустима, и это тот же принцип «пишем после ответа», что уже действует для решений.

### Судьба `AGENTGATE_TOKEN`

Остаётся, но только для localhost. Правило `validate_token_for_bind()` переворачивается:

- bind на localhost, ключей нет, `AGENTGATE_TOKEN` не задан → пускаем всех (как сейчас, режим разработки);
- bind на localhost, `AGENTGATE_TOKEN` задан → работает как раньше;
- **bind не на localhost → принимаются только выданные ключи**, `AGENTGATE_TOKEN` игнорируется, и сервис не стартует, если ни одного действующего ключа нет.

Причина: статический токен из переменной окружения нельзя ни отозвать, ни атрибутировать. На публичном адресе это неприемлемо, локально — удобно и безопасно.

### Что попадает в решения и в логи

`key_id` (не ключ) пишется в `DecisionRow` и в JSONL, чтобы решения можно было атрибутировать клиенту. Сам ключ и его хэш не логируются никогда, включая ответы об ошибках: `401` не сообщает, ключ отсутствует, просрочен или отозван — разница помогает подбирать.

## Чего сознательно не делаем в v1

Ротацию по расписанию, области действия (scopes) на ключ, ограничение частоты обращений по ключу, привязку ключа к профилю. Всё это осмысленно, но ни одно не требуется, чтобы сервис стал доступен по ключу, а `scopes` без продуманной модели прав — это сложность без гарантии.
