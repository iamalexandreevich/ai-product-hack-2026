## 1. Цель и границы

### 1.1. Две дыры, оставшиеся от v3.2

**Первая: `principal` держится на договорённости, а не на структуре.** `principal = coalesce(key_id, 'token')` работает ровно до тех пор, пока ни один `key_id` не равен строке `token`. Сегодня это гарантирует единственный факт: id ключа выпускается `str(ULID())` в `ApiKeyRepo.create`, и больше нигде. Гарантии не даёт ни база (`decisions.key_id` — просто `varchar(26)`, `api_keys.id` — тоже), ни код (никто не проверяет форму id перед записью). Это ровно тот класс инварианта, который спека v3.2 сама назвала в решении №4 («коллизия невозможна: `key_id` — ULID»), но нигде не выразила. Цена ошибки высокая и тихая: ключ с id `token` разделил бы пространство повторов со статическим токеном, то есть отдал бы аудит и уникальность `Idempotency-Key` чужому предъявителю. Docstring `principal_of` обещает это свойство читателю — обещание должна держать база, а не комментарий.

**Вторая: `Idempotency-Key` не привязан к сессии.** С v3.2 повтор живёт в границах предъявителя, но не сессии. Что это значит на практике сегодня:

- **Вердикт уже не путается.** `Replay.answers` сверяет `request.identity_digest()` — sha256 всего запроса без `metadata`, — а `session_id` входит в тело запроса. Значит, два вызова из разных сессий с одинаковым `Idempotency-Key` уже сейчас получают каждый своё решение, а не чужое.
- **Строка теряется.** Уникальный частичный индекс — по паре `(principal, idempotency_key)`. Второй вызов, из другой сессии того же предъявителя, попадает в `ON CONFLICT DO NOTHING`: `DecisionRepo.insert` вернёт `False`, писатель напишет warning, аудиторской строки не будет, и allow-кэш этой сессии не получит своей записи (она пишется только после успешной вставки).
- **Кэш повторов вытирает сам себя.** Ключ хранилища — `"{principal}:{key}"`. Две сессии, чередующие вызовы под одной строкой ключа, кладут записи в одну ячейку, и каждая затирает предыдущую: повтор не срабатывает ни для одной из них. Функция, ради которой заголовок существует, у такого клиента просто не работает.

Виноват в обоих случаях один и тот же клиент — тот, кто выбрал одну строку `Idempotency-Key` на две сессии, — но наказание несоразмерно: он теряет аудит и идемпотентность, хотя два его вызова заведомо различны (различны их дайджесты).

### 1.2. Что делает v3.3

1. Форма id ключа перестаёт быть договорённостью: один паттерн-константа в `domain/principal.py`, `CHECK` на `api_keys.id` и на `decisions.key_id` в базе, охранная проверка на месте выпуска id.
2. Границей повтора становится тройка `(principal, session_id, Idempotency-Key)`: ключ хранилища повторов, проверка в `answers`, восстановление из Postgres и уникальный индекс — все четыре места.

### 1.3. Чего v3.3 не трогает

- **Провод не меняется ни одним полем.** `DecideRequest`, `InspectRequest`, `DecideResponse`, `InspectResponse`, заголовки, `GET /v1/decisions` — всё как в v3.2. `contracts/` не перегенерируются; `git diff --exit-code ../contracts` пустой в каждой задаче.
- Каскад решения, ступень 1 и 2, инспект, пол строгости, правила — без изменений. Ни один вердикт не меняется.
- Статический токен по-прежнему принимается наравне с ключами; `key_id: null` — законное состояние строки.
- TTL повтора (`allow_cache_ttl_seconds`), поведение при отказе хранилища повторов, лимит в 128 символов на ключ, гонка двух одновременных повторов — как было.
- Атрибуция решения к ключу (`key_id` в строке, в JSONL и в ленте) сделана в v3.2 и здесь не переделывается.

## 2. Решения

| # | Решение | Почему так, а не иначе |
|---|---|---|
| 1 | Паттерн формы id живёт **один раз** — константой `KEY_ID_PATTERN` в `domain/principal.py`, рядом со `STATIC_PRINCIPAL` | Это ровно то знание, ради которого модуль существует: «кто такой принципал и почему литерал не может им притвориться». Три потребителя — `CheckConstraint` модели, охрана в `store/keys.py` и unit-тест «литерал не подходит под паттерн» — читают одну строку. Второй экземпляр паттерна в SQL миграции неизбежен (миграция обязана быть неподвижным слепком), и именно поэтому её текст сверяется тестом round-trip, а не глазами. |
| 2 | Проверка в базе — `CHECK`, а не `FOREIGN KEY decisions.key_id → api_keys.id` | FK связал бы горячую запись решения с таблицей ключей: удалить или пересоздать ключ стало бы невозможно без каскада по всей ленте, а отозванный ключ мы храним вечно именно для аудита. `CHECK` проверяет форму — единственное, что нам нужно, — и стоит доли микросекунды. Спека v3.2 §3.3 уже отказалась от FK по той же причине; v3.3 это решение не пересматривает. |
| 3 | `CHECK` вешается на оба столбца: `api_keys.id` и `decisions.key_id` | Один только `api_keys.id` не закрывает путь: `decisions.key_id` пишется из API-слоя строкой, пришедшей из кэша проверки ключа, и FK между ними нет (решение 2). Один только `decisions.key_id` не закрывает выпуск. Две разные точки входа — две проверки. |
| 4 | Охрана формы стоит в `store/keys.py::ApiKeyRepo.create`, на месте выпуска id | Валидация на границе (правило 7.1 стайл-гайда): id рождается здесь, и здесь единственное место, где его форма ещё может быть неверной по вине кода, а не по вине ручного `INSERT`. Проверять форму при каждом чтении ключа — защитное программирование внутри доверенной зоны. |
| 5 | Ключ хранилища повторов — `"{principal}:{session}:{key}"`, где `session` — `session_id` либо литерал `-` | Протокол `ReplayStore` остаётся односоставным (одна строка), `TtlStore` и его тесты не трогаются. Сентинел нужен ровно по той же причине, по какой нужен `principal`: `None` в ключе неотличим от отсутствия, а бессессионные вызовы — законное состояние, у которого должно быть своё пространство, а не общее со всеми. |
| 6 | Сентинел — `-`, а не пустая строка | Пустая строка даёт ключ вида `token::abc`, где двойное двоеточие читается как опечатка и провоцирует «почини». Одиночный дефис виден, печатается в логе и не встречается в ULID. |
| 7 | `Replay` **не** получает поля `session`; `answers(request, principal)` не меняет сигнатуру | Наименьшая верная форма. `session_id` входит в тело запроса, а `request_digest` — это sha256 всего тела без `metadata`, поэтому проверка сессии уже выполняется, причём строже (совпасть должно всё тело, не только сессия). Поле `Replay.session` было бы вторым хранением того же знания (правило 1.3 стайл-гайда) и разошлось бы с дайджестом при первой же правке `identity_digest`. Отличие от `principal`: тот в тело запроса не входит вовсе, поэтому там второй замок был не копией, а единственным. Инвариант «повтор не отвечает чужой сессии» от этого не слабеет и проверяется тестом (§7.2). |
| 8 | Уникальность в базе — по тройке `(principal, session_id, idempotency_key)` с `NULLS NOT DISTINCT` | `session_id` nullable, а в Postgres `NULL <> NULL`: без флага бессессионные вызовы одного предъявителя с одним ключом перестали бы конкурировать за уникальность вовсе — ровно та дыра, которую v3.2 закрывала генерируемым `principal`. `NULLS NOT DISTINCT` (Postgres 15+, у нас 16) делает `NULL` равным `NULL` внутри индекса и позволяет обойтись без второго генерируемого столбца. SQLAlchemy 2.0.52 (в дереве) знает `postgresql_nulls_not_distinct`; фолбэк на генерируемый `session_scope = coalesce(session_id, '-')` не понадобился и не делается. |
| 9 | Два файла миграции в одном релизе: `0008_key_id_shape` и `0009_session_idempotency` | Один релиз, одна голова, `alembic upgrade head` линеен — но два **файла**, потому что задачи 1 и 3 плана идут разными исполнителями, а два агента, редактирующих один файл миграции, — гарантированный конфликт и потерянная половина. Цена разделения нулевая: `0009` не читает ничего из `0008`. |
| 10 | `0008` не чинит данные, а падает на невалидной строке | Невалидный `key_id` в исторических данных означал бы, что кто-то писал в базу мимо сервиса; молча вычистить такую строку — уничтожить след инцидента. Правильный ответ — остановить миграцию и показать строки оператору. Ожидаемое число таких строк — ноль: `key_id` появился в `0007`, а писать его умеет только `_answer` из значения, пришедшего от `ApiKeyRepo`. |

## 3. Форма `key_id`

### 3.1. Паттерн

```python
# domain/principal.py
STATIC_PRINCIPAL = "token"
KEY_ID_PATTERN = r"^[0-9A-HJKMNP-TV-Z]{26}$"
```

Crockford base32 в верхнем регистре: цифры и буквы без `I`, `L`, `O`, `U`. Ровно 26 символов — длина ULID. `STATIC_PRINCIPAL` под этот паттерн не подходит по двум независимым причинам сразу (строчные буквы, длина 5), и это утверждение — unit-тест, а не замечание в докстринге.

Паттерн описывает **форму**, а не валидность ULID: он пропустит строку, у которой первый символ больше `7` (то есть метка времени за пределами 10889 года). Это сознательно — нам нужно множество, не пересекающееся с `"token"` и стабильное в SQL, а не второй парсер ULID.

### 3.2. Проверка в базе

```python
# store/models.py, class ApiKeyRow
__table_args__ = (
    CheckConstraint(f"id ~ '{KEY_ID_PATTERN}'", name="ck_api_keys_id_ulid"),
)

# store/models.py, class DecisionRow.__table_args__ (добавляется к существующим)
CheckConstraint(
    f"key_id IS NULL OR key_id ~ '{KEY_ID_PATTERN}'", name="ck_decisions_key_id_ulid"
),
```

`key_id IS NULL` разрешён явно: `null` — это статический токен, законное и частое состояние строки (§1.3). Оператор `~` — POSIX-регексп Postgres; `^`/`$` в нём привязаны к границам строки, многострочного режима по умолчанию нет.

### 3.3. Охрана на месте выпуска

```python
# domain/principal.py
def ensure_key_id_shape(key_id: str) -> str:
    """The id a key is minted with, or ValueError.

    The shape is what keeps an issued key from ever being the static
    principal, and the database says the same thing in ck_api_keys_id_ulid.
    A caller that mints ids some other way fails here, not two tables later.
    """
    if re.fullmatch(_KEY_ID_RE, key_id) is None:
        raise ValueError(f"key id is not a ULID: {key_id!r}")
    return key_id
```

Вызывается один раз — в `ApiKeyRepo.create`, вокруг `str(ULID())`. Больше нигде: чтение ключа, проверка на горячем пути и запись решения формы не проверяют (решение 4).

### 3.4. Миграция `0008_key_id_shape`

`revision = "0008"`, `down_revision = "0007"`. `upgrade` добавляет два `CHECK`; `downgrade` их снимает. Оба направления безопасны: `downgrade` только ослабляет ограничение и данных не трогает. `upgrade` упадёт, если в `api_keys.id` или в `decisions.key_id` есть строка вне формы (решение 10) — этот случай описан в `service/README.md` рядом с уже описанной опасностью отката `0007`.

## 4. `Idempotency-Key` в границах сессии

### 4.1. Ключ хранилища

```python
NO_SESSION = "-"


@dataclass(frozen=True)
class ReplayKey:
    principal: str
    session: str
    key: str

    @classmethod
    def of(cls, key_id: str | None, session_id: str | None, key: str) -> "ReplayKey":
        return cls(principal_of(key_id), session_id or NO_SESSION, key)

    def storage_key(self) -> str:
        return f"{self.principal}:{self.session}:{self.key}"
```

Разбирать эту строку обратно нигде не требуется, поэтому экранирования нет. Два следствия названы прямо, потому что оба безобидны и оба удивляют при первом чтении:

- сессия, буквально названная `-`, делит ячейку с бессессионными вызовами;
- `session_id`, содержащий `:`, может дать ту же склейку, что другая пара (сессия, ключ).

В обоих случаях худшее, что происходит, — две записи вытесняют друг друга из кэша и повтор просто не срабатывает: подмены вердикта не будет, потому что `answers` сверяет дайджест всего запроса, а он у этих вызовов разный. Идемпотентность — оптимизация; корректность держит дайджест.

### 4.2. Вызов из API

`api/app.py::_answer` уже разобрал тело до построения ключа, поэтому сессия берётся из разобранного запроса, а не из сырого JSON:

```python
key = _replay_key(request)
replay_key = ReplayKey.of(key_id, parsed.session_id, key) if key is not None else None
```

`DecideRequest.session_id` и `InspectRequest.session_id` — оба `str | None`, оба присутствуют в обеих моделях, поэтому одна строка обслуживает оба маршрута и `RouteSpec` не растёт ни на поле.

### 4.3. `Replay`

Не меняется (решение 7). `answers(request, principal)` остаётся как есть: дайджест всего тела уже включает `session_id`, и это единственное место, где знание «эта запись принадлежит той сессии» хранится.

### 4.4. Восстановление из Postgres

```python
await self._inner.put(
    ReplayKey.of(record.key_id, record.session_id, record.idempotency_key).storage_key(),
    replay, remaining,
)
```

`DecisionRecord.session_id` уже есть (v1), отдельного чтения не требуется. После рестарта запись оказывается ровно в той ячейке, в какой была до него.

### 4.5. Уникальность в базе

Было (v3.2):

```python
Index("ux_decisions_principal_idempotency_key", "principal", "idempotency_key", unique=True,
      postgresql_where=text("idempotency_key IS NOT NULL"))
```

Стало:

```python
Index(
    "ux_decisions_principal_session_idempotency_key",
    "principal", "session_id", "idempotency_key", unique=True,
    postgresql_where=text("idempotency_key IS NOT NULL"),
    postgresql_nulls_not_distinct=True,
)
```

Частичная семантика сохранена: строка без `Idempotency-Key` в индекс не входит и за уникальность не конкурирует. `NULLS NOT DISTINCT` нужен ровно для бессессионных вызовов (решение 8).

`DecisionRepo.insert` меняет цель вывода конфликта:

```python
stmt = pg_insert(table).values(**values).on_conflict_do_nothing(
    index_elements=[table.c.principal, table.c.session_id, table.c.idempotency_key],
    index_where=table.c.idempotency_key.isnot(None),
)
```

Postgres выводит арбитра по набору столбцов и предикату; уникальный индекс с `NULLS NOT DISTINCT` для вывода пригоден (15+). `principal` по-прежнему генерируемый и в `values` не попадает — `store/mapper.py::_GENERATED` не меняется.

### 4.6. Миграция `0009_session_idempotency`

`revision = "0009"`, `down_revision = "0008"`. `upgrade` снимает `ux_decisions_principal_idempotency_key` и создаёт индекс по тройке с `postgresql_nulls_not_distinct=True`. `downgrade` делает обратное — и это **сужающая** операция: если после апгрейда один предъявитель успел записать один и тот же `Idempotency-Key` в двух сессиях, откат упадёт на создании узкого индекса, и строки придётся де-дуплицировать вручную. Та же по природе опасность, что у `downgrade` миграции `0007`, и описывается она там же, в `service/README.md`.

### 4.7. Что остаётся как было

- Повтор в той же сессии под тем же ключом и с тем же телом — тот же `decision_id`, одна строка, счётчики не двигаются.
- Повтор под другим предъявителем — своё решение и своя строка (v3.2, не отменяется).
- Повтор после истечения TTL решается заново, а его строка не попадает в базу из-за уникального индекса — теперь по тройке. Ограничение остаётся в корневом `CLAUDE.md`, меняется формулировка.
- Гонка двух одновременных повторов с одним ключом по-прежнему сдвигает счётчики сессии дважды.
- Отказ хранилища повторов — «повтора нет», никогда 5xx.

## 5. Контракт

**Не меняется.** Ни одного нового поля, ни одного нового заголовка, ни одного изменения в `GET /v1/decisions`. `contracts/decide_request.schema.json`, `contracts/inspect_request.schema.json`, `contracts/openapi.yaml` остаются байт в байт; `tests/test_contracts.py` — регресс на это.

Меняется **семантика** одного уже существующего заголовка, и это описывается прозой в трёх местах:

- `contracts/README.md` — раздел про `Idempotency-Key`: требование «уникален на вызов инструмента» ослабляется до «уникален на вызов инструмента в границах предъявителя и сессии».
- `docs/connect.md` — абзац про границы ключа: к предъявителю добавляется сессия.
- `service/README.md` — раздел про миграции: `0008` (два `CHECK`, падение на невалидной строке) и `0009` (тройка, `NULLS NOT DISTINCT`, опасность сужающего отката).

Правило `contracts/README.md` про упоминание трёх направлений в PR действует и здесь: текст меняется, хотя схема — нет.

## 6. Инварианты

1. Ни один вердикт не зависит ни от `key_id`, ни от `session_id` в роли границы повтора: сессия влияет на решение только через тело запроса, как и раньше.
2. `STATIC_PRINCIPAL` не подходит под `KEY_ID_PATTERN`. Это утверждение проверяется тестом, а не рассуждением.
3. Ни один выпущенный ключ не может получить id вне формы: охрана в `ApiKeyRepo.create` и `ck_api_keys_id_ulid`.
4. Ни одна строка решения не может нести `key_id` вне формы: `ck_decisions_key_id_ulid`. `NULL` разрешён.
5. Один `Idempotency-Key` + одно действие + один предъявитель + **разные** сессии → два разных `decision_id` и **две** строки в `decisions`.
6. Один `Idempotency-Key` + одно тело + один предъявитель + одна сессия → один `decision_id` и одна строка.
7. Два бессессионных вызова одного предъявителя с одним ключом и разными телами по-прежнему конкурируют за уникальность (`NULLS NOT DISTINCT`): вторая строка не пишется. Границей служит `-`, а не «всё разрешено».
8. Форма ответа не меняется: `key_id` не попадает ни в `DecideResponse`, ни в `InspectResponse`.
9. `alembic upgrade head` линеен: `0007 → 0008 → 0009`, одна голова.
10. Бюджет ступени 1 p50 ≤ 1 мс не затронут: ни один `CHECK` и ни один индекс не лежат на пути вердикта — они лежат на пути записи, которая идёт после ответа.

### 7.2. Критерии приёмки

1. `alembic upgrade head` на базе с данными проходит; `\d+ decisions` показывает `ck_decisions_key_id_ulid` и `ux_decisions_principal_session_idempotency_key` с `NULLS NOT DISTINCT`; `\d+ api_keys` — `ck_api_keys_id_ulid`.
2. Ручной `INSERT` в `decisions` с `key_id = 'token'` отвергается базой.
3. Один `Idempotency-Key` и одно действие под одним ключом из сессий `s1` и `s2` → два разных `decision_id`; `select principal, session_id, count(*) from decisions where idempotency_key = …` даёт две строки по единице.
4. Тот же ключ, та же сессия, дважды → один `decision_id`, одна строка.
5. `alembic downgrade 0007 && alembic upgrade head` на чистовой базе проходит в обе стороны.
6. Полный прогон зелёный, собрано не меньше 1509 тестов, `git diff --exit-code ../contracts` пустой.

### 7.3. Не входит

- Привязка `Idempotency-Key` к `call_id` или к чему-либо ещё, кроме принципала и сессии.
- Блокировка ключа «в полёте»: гонка двух одновременных повторов по-прежнему сдвигает счётчики дважды.
- FK `decisions.key_id → api_keys.id` — сознательно нет (решение 2).
- Строгий вариант `api-keys.md` («non-localhost принимает только ключи»).
- Единый на весь сервис отзыв ключа: кэш проверки остаётся per-process.
- Отказ от бессессионных вызовов: `session_id: null` остаётся законным, и `-` — его полноправное пространство.
