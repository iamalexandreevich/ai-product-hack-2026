# Сверка с контрактом адаптера (Gate ↔ Guard, protocol 1)

Дата: 3 сентября 2026. Источник: `gate-openapi.yaml`, предоставлен владельцем продукта.
Статус: анализ расхождений. Целевой контракт — сделать такой же.

Контракт описывает плагин Gate внутри opencode 1.x / Kilo CLI / opencode 2.0, ходящий в гард-сервис. Плагин → гард; гард плагин не вызывает.

## Главный вывод

Контракт адаптера почти точно совпадает с нашей **конечной точкой v4**. Он не конкурирует с дорожной картой — он описывает её же с другой стороны.

| Возможность адаптера | Наша версия |
|---|---|
| `direction: out` — тулкол до выполнения, вердикт `allow \| ask \| deny` | **v1** (есть) |
| `session.messages` — вся история в каждом запросе | **v2** |
| `direction: in` — оценка результата тула | **v3** |
| `verdict: mask` + переписанный `output` | **v4** — это и есть Context Guard |
| `provenance: {kind, ref}` у результата | **v3** (в спеке v3 отмечено как обязательное) |

Совпало и то, что мы вывели независимо: `mask` — ровно «маскирование промпт-инъекций внутри tool-result», а `provenance` — то, без чего пометка результата не переживает переход к следующему действию.

## Расхождение, которое надо решить до интеграции

**Клиент по умолчанию fail-open. Мы — жёстко fail-closed.**

Контракт адаптера: «недоступность / таймаут / невалидный ответ → fail-open (`allow` / `pass`), либо fail-closed при `GATE_FAIL_CLOSED=1`».

Наше глобальное ограничение: «любая ошибка, таймаут, невалидный ответ, невалидный запрос → `ask`; `allow` по ошибке невозможен».

Это не разница формулировок, а противоположные позиции. Сервис выстроен так, что `allow` по ошибке недостижим ни по одному пути — на это есть тесты, и в Task 7 это проверялось исполнением. Но если клиент по умолчанию трактует недоступность гарда как `allow`, гарантия снимается **снаружи**: положил гард — разрешено всё.

Три варианта, решение владельца продукта:

1. интеграция требует `GATE_FAIL_CLOSED=1` как условие поддерживаемой конфигурации;
2. принимаем fail-open на клиенте как осознанный размен на доступность и убираем утверждение «allow по ошибке невозможен» из описания системы в целом — внутри сервиса оно останется верным;
3. договариваемся с направлением адаптеров о смене умолчания.

Молчаливо оставить как есть — худший исход: сервис утверждает одно, система ведёт себя иначе.

## Идемпотентность — задевает Task 9 и Task 10

Контракт: «Запросы идемпотентны по `(harness.name, session.id, call.id | result.call_id, direction)` — гард может получить повтор».

У нас идемпотентности нет. Повторный `decide` создаст вторую строку решения и **дважды сдвинет счётчики сессии** — повтор из-за сетевого таймаута приблизит эскалацию, хотя действие было одно.

Не вносил в Task 9 на ходу: она уже в работе, и это расширение плана, а не находка ревью. Но `DecisionRow` нужен ключ идемпотентности, а `SessionRepo` — защита от двойного учёта.

## Остальные расхождения формы

| | Адаптер | Мы (v1) |
|---|---|---|
| Эндпоинт | один `POST /check`, ветка в поле `direction` | `POST /v1/decide` |
| Здоровье | `GET /health`, отдаёт `protocol` | `GET /healthz` |
| Версия протокола | поле `protocol: 1` в каждом запросе | нет |
| Имя вердикта | `verdict` | `decision` |
| Инструмент | свободная строка (`bash`, `edit`, `read`, `webfetch`, `task`, `mcp__server__tool`) | enum из пяти значений |
| Аргументы | `call.input` — объект как есть | `raw` + типизированный `args` |
| Сессия | дерево: `root_id`, `parent_id`, сабагенты | плоский `session_id` |
| Параллельные вызовы | `call.batch` — ID других тулколов того же хода | нет понятия |
| Провенанс автора | `author: human \| agent \| system` у каждого сообщения | нет |
| Причина отказа | `reason`, уходит модели как текст ошибки тула | `reason` + `suggest` |
| Телеметрия | `direction: event` (`permission.replied`, `mode.changed`, …) | нет |
| Режим гейта | `mode: auto \| ask \| allow \| off` в запросе | режим на стороне профиля |

## Что стоит взять раньше своей версии

Три вещи дёшевы сейчас и дороги потом.

**1. Поле версии протокола.** Добавить в `DecideRequest`/`DecideResponse` сейчас — одна строка. Добавлять после того, как на контракт сядут три харнесса, — согласование.

**2. `author: human | agent | system`.** Это ровно то различие, ради которого делается v2: `user`-сообщение, сочинённое родительской моделью для сабагента, не является запросом человека. Без этого поля история v2 будет вводить классификатор в заблуждение — он примет текст агента за намерение пользователя. Заложить в схему истории сразу.

**3. `reason` не должен раскрывать механику правил.** У адаптера записано явно, у нас нет. Наши `reason` сейчас называют `rule_id` и пороги; они уходят модели, а значит и потенциальному атакующему — как разведданные о том, что именно сработало.

## Что делать дальше

v1 доводим как запланировано: расхождения выше на неё не влияют, кроме идемпотентности, которая относится к Task 9 и Task 10. Приведение к контракту адаптера — отдельная работа поверх v2–v4, и её объём в основном совпадает с уже спланированным.
