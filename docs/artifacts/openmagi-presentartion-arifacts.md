# Изначальные требования к проекту:

Описание
Продукт или процесс, к которому относится кейс
ИИ-кодинг-агенты наподобие Claude Code стали повседневным инструментом разработчиков. Агент пишет код, устанавливает зависимости, тестирует и часто даже самостоятельно развёртывает приложение, а человек валидирует действия и результаты «на вайбе».

Продуктивность такого режима резко возрастает, когда агенту дают автономию и разрешают действовать без подтверждения каждого шага. Однако возникает вопрос: что может пойти не так, когда агент вправе самостоятельно запустить от имени пользователя любую команду на его машине?

В чём боль и сколько она стоит бизнесу сейчас
Разработчики оказываются между двумя крайностями:

перепроверять каждое действие агента — сталкиваться с approval fatigue и резко терять в продуктивности;
запускать агента с --dangerously-skip-permissions — принимать риск серьёзных инцидентов.
Без достаточного контроля агент может установить вредоносный npm-пакет, раскрыть секреты, следуя инструкции из заражённого навыка, или удалить промышленную базу данных. В результате рост продуктивности оборачивается финансовыми потерями.

Особенно остро проблема стоит для пользователей open-source-моделей. По данным исследования TRAP, на одном наборе атак доля успешных инъекций составляет 13 % для GPT-5 и 43 % для DeepSeek-R1. При использовании менее устойчивой модели встроенной защиты агента может быть недостаточно.

Кто пользователь решения и как он им пользуется
Основной пользователь — разработчик, работающий с кодинг-агентом в IDE или CLI.

Помимо режимов ask permission и bypass permissions появляется auto mode. Система самостоятельно оценивает безопасность команды, блокирует опасные вызовы или передаёт решение разработчику.

14 августа auto mode стал режимом по умолчанию в Claude Code, но в open-source-решениях сопоставимого движка пока нет. Например, в Kilo Code открыт issue о воспроизведении этого функционала.

Чем надёжнее кодинг-агент, тем охотнее его выбирают разработчики и разрешают использовать компании.

Постановка задачи и этапы работы
1. Исследование угроз
Изучить распространённые угрозы вайбкодинга, например:

неосторожные действия агента;
slopsquatting;
prompt injection в SKILL.md, README, MCP и других источниках инструкций;
внедрение вредоносной конфигурации;
downgrade-атаки;
утечки данных через контекст и вызовы инструментов
2. Анализ существующих решений
Проанализировать механизмы безопасности во фронтирном Claude Code и популярном open-source-кодинг-агенте Kilo Code.

3. Реализация auto mode
Реализовать для Kilo Code режим auto mode, вдохновлённый Claude Code. В качестве ориентира можно использовать техническое задание из GitHub issue.

Команда самостоятельно выбирает и приоритизирует функции, которые успеет реализовать за время хакатона.

4. Сборка бенчмарка
Создать бенчмарк для оценки качества защиты как от вредоносных, так и от неосторожных действий агента.

5. Продолжение работы после блокировки
После блокировки действия агент должен получить информацию о блокировке и безопасно продолжить работу. Необходимо продумать удобный и защищённый сценарий такого взаимодействия.

6. Дополнительные функции защиты
Дополнительные баллы можно получить за:

рекомендуемые списки allow, deny и ask для команд и директорий;
модуль защиты от slopsquatting;
другие улучшения, повышающие современный уровень безопасности кодинг-агентов.
7. Анализ слабых мест
Честно проанализировать ограничения решения и риск того, что необоснованное расширение автономии агента может снизить безопасность.

8. Вклад в Kilo Code
Дополнительные баллы предусмотрены за содержательный pull request в Kilo Code, повышающий уровень безопасности вайбкодинга в Восточной Европе.

Дополнительные сведения по кейсу
К началу хакатона кейсодатель предоставит:

стартовый датасет примерно из 20 обычных задач разработки для оценки эффективности;
стартовый датасет примерно из 20 атак, от которых необходимо защититься.
Участникам предлагается расширить этот датасет в рамках своего исследования.

Ожидаемый результат
Ожидаемый результат

2. Обновлённый Kilo Code

Требования и примечания
Защита от slopsquatting должна работать внутри кодинг-агента и вызываться до установки пакета, а не в pre-commit-хуках или CI. Она должна защищать не только от известных вредоносных пакетов, но и от угроз нулевого дня.
Хотя бы один добавленный контроль должен быть архитектурно неуязвим к prompt injection. Гардрейлы обходятся слишком легко, поэтому в системе должны быть инструменты, до которых инъекции не доходят.
Кейс намеренно сформулирован широко. Команда самостоятельно выбирает наиболее острую проблему — prompt injection, slopsquatting, небезопасные вызовы, эксфильтрацию данных, недостаточную наблюдаемость или другую угрозу — и точку применения контролей.
Код теперь пишет агент. Самое важное — понимать назначение кода и уметь доказать, что он выполняет заявленные функции.
Целевая метрика и что считаем успехом
Количественные метрики
ASR ↓ — доля атак, которые привели к ущербу. Рассчитывается на базовом наборе и атаках, собранных командой. Главная метрика; показывает, работает ли защита в принципе.
Utility ↑ — доля успешно завершённых легитимных задач. Без неё любая защита может выглядеть идеальной, поскольку самый надёжный способ защиты — не позволять агенту работать.
FP ↓ — количество блокировок и лишних подтверждений на легитимных задачах. Показывает цену безопасности для разработчика: инструмент, который часто ошибается, отключают.
Friction ↓ — количество решений, которые система требует от человека. Чем чаще агент задаёт вопросы, тем меньше выигрыш от автономии.
Latency ↓ — задержка на одно решение и замедление задачи в целом. Проверка, которая занимает больше времени, чем само действие, нарушает рабочий процесс агента.
Качественные критерии
Глубина проработки и покрытие атак. Оценивается, насколько решение ушло от поверхностной защиты, включая атаки, распределённые по нескольким действиям, и неявную установку вредоносного пакета.
Качество метода. Необходимо объяснить происхождение чисел, а также методику сборки и запуска бенчмарка. Отрицательный результат с понятным методом ценнее хорошего числа без описания метода.
Честность гарантий. Требуется описать ограничения: что система гарантирует всегда, а что обеспечивает по возможности.
Исследование approval fatigue — дополнительные баллы. Можно собрать статистику о том, как часто люди пропускают опасные команды по сравнению с предлагаемым решением. Это ключевой критерий перевода auto mode в режим по умолчанию в Claude Code.

# Требования к презентации и выступлению:
## Регламент (жёсткие рамки)

- **5 минут** на питч. После 5:00 выступление обрывают → целевая длительность 4:40–4:50.
- **3 минуты** на вопросы комиссии.
- **Один основной спикер**: переходы между людьми съедают время.
- Всё открыто заранее: презентация, демо, ссылки, логины, резервная запись.

## Обязательная структура пяти минут

| Время | Блок | Что должно прозвучать |
|---|---|---|
| 0:00–0:30 | Продукт | что создали, для кого, какая проблема |
| 0:30–1:00 | Ценность | что станет быстрее / дешевле / точнее |
| 1:00–3:10 | Демо | один сценарий целиком |
| 3:10–4:10 | Техника | архитектура, данные, модели, метрики, ограничения, вклад команды |
| 4:10–5:00 | Финал | готовность, следующий шаг, заключительная фраза на 10–15 секунд |

## Критерии оценки: 5 × 0–3 балла

Кейс · Ценность · Техника · Прототип · Защита.
**3 балла ставят только тогда, когда вывод подтверждён фактом, тестом или показан в демо.** Всё остальное — потолок ниже.

## Требования к содержанию блоков

**Открытие (30 с).** Формула: «Мы создали *[продукт]* для *[пользователя]*, который решает *[проблему]* с помощью *[принципа]*». Пересказ условия кейса и нерасшифрованные термины запрещены.

**Ценность.** Цепочка «процесс → пользователь → эффект». Формулировка должна содержать число, базу сравнения и условия замера («2 минуты вместо 12, проверили на 30 примерах»). Измеренное отделяется от гипотезы явно, с указанием, как гипотезу будут проверять.

**Демо.** Ровно один сценарий: входные данные → действие пользователя → работа системы → результат → ценность. Обход функций продукта не засчитывается. Обязателен план Б — видео, GIF или серия скриншотов того же сценария; чинить демо на сцене нельзя.

**Техчасть (1 мин).** 2–4 ключевых компонента и связи между ними, поток данных, обоснование выбора подхода, что команда сделала сама, ограничения и риски. Перечисление стека и названий моделей без причины не защищает решение. Детали уходят в вопросы или appendix (приложение к презентации).

**Финал.** Три разделённые категории: **сделано** (работает и показано в демо, сценарий воспроизводим, видно вклад команды), **проверено** (тесты/метрики или честное «пока нет», ограничения названы), **планируется** (следующий шаг на 2–4 недели, критерий успеха, кто принимает решение). Последняя фраза на 10–15 секунд пишется дословно и не импровизируется: ценность + что доказано + следующий шаг + конкретный запрос.

## Слайды

- 5–7 содержательных слайдов, порядок: ценность → проблема → путь → демо → архитектура → метрики → следующий шаг.
- Одна мысль на слайд, минимальный кегль 30, заголовок формулируется как вывод.
- Голос не дублируется полным текстом; скриншот обрезан до важного места; график подписан выводом; хронология работы команды не показывается.

## Работа с «проклятием знания»

Аббревиатуры расшифровываются при первом употреблении плюс бытовой синоним; после каждой ключевой мысли — пауза; на каждую абстракцию — пример, скриншот или цифра. Проверка: человек не из вашей области должен суметь пересказать проект.

## Вопросы (3 минуты)

Дослушать → при многослойном вопросе уточнить → ответить за 30 секунд по схеме «прямой ответ → один факт → ограничение или следующий шаг» → спросить «ответил на вопрос?». Если ответа нет — обозначить гипотезу и способ проверки, без перекладывания ответственности. Заранее готовятся ответы: почему не взяли готовое решение, сколько стоит, что с данными, кто поддерживает, что если метрика упадёт.

## Финальный чек перед выходом

- Питч укладывается в 4:40–4:50.
- Основной спикер выбран.
- Назначены ответственные за продуктовые и технические вопросы.
- Проведены две репетиции с таймером.

### Правила
- Фон всегда `bg`. Максимум два фона на экран: `bg` + `panel`.
- `brand` используется заливкой (не текстом на тёмном — контраст низкий). Текст на `brand` — `text` или `on-purple`.
- `lime` — только как сигнал/заголовок. Никогда как фон больших областей.
- Текст на цветных плашках (`lime`, `deny`, `ask`) — `bg` (#0B0714).
- Градиентов нет. Скруглений нет (radius 0). Теней нет.

## 3. Компоненты

### 3.1 Вердикты (allow / deny / ask)
Плашка без скруглений, padding 10px 16px, текст `bg`. Слева иероглиф (Noto Sans JP 900, 22px), справа две строки: название (Big Shoulders 900, 18px, letter-spacing .04em) и пояснение (mono 10px).

| decision | Иероглиф | RU | Фон | Пояснение |
|---|---|---|---|---|
| allow | 承認 | РАЗРЕШЕНО | `lime` | allow · кэш на сессию |
| deny | 否定 | ЗАПРЕЩЕНО | `deny` | deny · причина агенту |
| ask | 審議中 | НА РАССМОТРЕНИИ | `ask` | ask · спросить пилота |

Компактная форма для строк лога: только иероглиф + слово тем же цветом текста на `panel`.

### 3.2 Панель MAGI (три судьи)
Сетка 3 колонки, gap 4px, без скруглений, min-height 130px, padding 16px.

| Блок | Соответствие | Заливка | Статус |
|---|---|---|---|
| MELCHIOR·1 | Ступень 1 — детерминированная (hard-deny → профиль → provenance → allowlist, ~1 мс) | `brand`, текст `text` | `■ ONLINE` лаймом |
| BALTHASAR·2 | Ступень 2 — локальная модель (Qwen 0.8–4B, первый токен A/D/U, 30–100 мс) | `brand` | `■ ONLINE` лаймом |

## 5. Голос и словарь
- Язык интерфейса — русский, служебные метки — латиница в верхнем регистре, вердикты дублируются иероглифом.
- Тон: сухой, командный, без восклицаний. «Вердикт», «ступень», «профиль», «пилот» (= разработчик), «харнесс».
- Кодовые имена: MAGI — сама двухступенчатая система решений; MELCHIOR·1 / BALTHASAR·2 / CASPER·3 — ступени; UNIT-xx — цветовые категории; NERV · TOKYO-3 — декоративные метки штаба.
- Всё остальное из вселенной — атмосфера, не функция. Оригинальный арт (Евы, персонажи, кадры) — только собственный или лицензированный, через слоты.
