Ключ памяти - (dialog_id, operator_id). epk_id_ul сюда передаётся, но его не
использует ни одно из четырёх хранилищ: VoiceCopilotPostgresSessionStorage._get_data
кладёт в WHERE только dialog_id/operator_id (postgres.py:160-161), а
InMemoryVoiceCopilotSessionStorage._get_data игнорирует его явно (in_memory.py:102).
То есть клиент в ключ памяти не входит вовсе, а окно чата оператора живёт дольше

Воспроизведено на ветке: тот же оператор, то же окно, epk_id_ul 111 -> 999.
Сессия клиента B приходит с историей клиента A и с его состоянием авторизации:
  is_authorized=True, authority='3', inn='7700000001', accounts=['сч-A']
Executor._ensure_authorization (executor.py:64) при is_authorized=True сразу
делает return, полномочия не перезапрашиваются. Итог: агент отвечает новому
клиенту на полномочиях и счетах предыдущего.

Ключ памяти должен включать клиента, либо смена epk_id_ul обязана сбрасывать
авторизацию и данные клиента (is_authorized, authority, accounts, cashiers_info,
inn, detailed_client_data, client_details_loaded).

Ключ записи и ключ чтения разные, и апсерт не чинит расхождение:
INSERT идёт ON CONFLICT (session_id) (строка 130), а DO UPDATE обновляет только
context и last_time_updated - operator_id и dialog_id остаются от первого писателя
строки. Читается же строка по (dialog_id, operator_id).

Сценарий: первый ход диалога пришёл без operator_info -> строка создана с
operator_id=''. Второй ход несёт operator_id='op-1' -> SELECT не находит строку ->
создаётся новая Session с тем же id=work_id -> INSERT попадает в ON CONFLICT ->
context перезаписывается, operator_id остаётся ''. Дальше КАЖДЫЙ ход стартует с
пустой историей, а накопленный контекст затирается. Память для этого диалога
не восстановится никогда.

Важно: две реализации ведут себя по-разному на одном и том же входе. На in-memory
я воспроизвёл этот сценарий - там потеря разовая (следующий save чинит _meta),
в Postgres она постоянная. Хранилища должны быть эквивалентны, иначе поведение
пилота зависит от SESSION_STORAGE_TYPE.

Лечится уникальным ключом по (dialog_id, operator_id): тогда апсерт и поиск
совпадают, а ORDER BY last_time_updated DESC LIMIT 1 в SELECT становится не нужен.

Дефолт SESSION_STORAGE_TYPE=inmemory (строка 142), а прод поднимается как
gunicorn --workers 2 --max-requests 500 (src/app/start.py:15,18).

Для всех остальных поверхностей память в процессе была необязательной: историю
восстанавливал sync_with_external_dialogue из полного диалога в запросе. Для
VOICECOPILOT поверхность шлёт только текущую реплику, значит хранилище стало

конфигурации диалог теряет контекст при попадании на соседний воркер.

Для копилота inmemory надо либо запретить (падать на старте, если
SESSION_STORAGE_TYPE != postgres при включённом пилоте), либо явно пометить как
режим только для локальной разработки.

Чтение памяти итерирует разделяемый _meta без блокировки. Прод -
gunicorn --worker-class gthread --threads 2, то есть два запроса VOICECOPILOT
живут в одном процессе на общем словаре.

Воспроизведено: пока один поток идёт по _meta.items() в _get_data, другой делает
self._meta[session.id] = (...) в _save_data ->
RuntimeError: dictionary changed size during iteration, 79 срабатываний на 3000
чтений. Исключение проглатывается SessionStorage.get (storages/base.py:53) ->
возвращается None -> диалог молча начинается с нуля, а в логах только
"Сессия не найдена". Это тихая потеря памяти под нагрузкой, которую невозможно
отличить от нормального промаха.

Тем же кодом: линейный проход по ВСЕМ сессиям процесса на каждый запрос и
datetime.now() внутри цикла. Плюс _meta не чистится никогда - TTL только
фильтрует чтение. Прогон подтвердил: после истечения TTL запись остаётся и в
_data, и в _meta, просто перестаёт находиться. Память процесса растёт
неограниченно.

Сброс памяти реализован подменой метода экземпляра

Контракт хранилища расширен тремя опциональными параметрами ради одной
поверхности. epk_id_ul не использует ни одна из четырёх реализаций,
dialog_id/operator_id игнорируют две из четырёх - докстринг на 44-46 это прямо
признаёт.

Но у копилота не другой контракт, а другой КЛЮЧ памяти: (dialog_id, operator_id)
вместо workId. Если считать ключ в create_executor - единственном месте, которое
знает про поверхность - и передавать его как обычный session_id, то:
  - базовые сигнатуры остаются как в agentsamo;
  - InMemoryVoiceCopilotSessionStorage исчезает целиком;
  - в таблице появляется PRIMARY KEY (dialog_id, operator_id), и вместе с ним
    пропадает ORDER BY ... LIMIT 1, а заодно и расхождение ключей записи/чтения
    (см. postgres.py:131);
  - выбор хранилища схлопывается с четырёх веток до двух.
Остаётся единственное настоящее отличие копилота - TTL, и его хватает одного WHERE.

Это же убирает целый класс расхождений между двумя реализациями памяти, из-за
которых сейчас поведение зависит от SESSION_STORAGE_TYPE.

Из save() убран отдельный try/except вокруг сериализации (сверь с
agentsamo/.../storages/base.py). Теперь сбой сериализатора логируется как
«Ошибка сохранения данных сессии ... в хранилище», то есть маскируется под сбой БД -
а для памяти это два совершенно разных инцидента.

Причина изменения контракта _save_data(session_id, data) -> _save_data(session) -
только чтобы дотянуться до session._operator для ключевых колонок. При ключевом
подходе (storages/base.py:37) она отпадает, и строка
data = self._serializer.serialize(session) перестанет дублироваться в четырёх
реализациях.

OperatorInfo не окупается. Ради двух строковых полей заведены: dataclass, параметр
конструктора Session, свойство, ветка в сериализаторе, ветка в десериализаторе,
экспорт в __init__ и два kwargs в update_request_identity - и половину из этого
уже забыли обновить (__eq__, __repr__, реэкспорт, из-за которого не собираются
тесты).

Единственные потребители _operator - два _save_data, которые рядом читают
session._channel.dialog_id: то есть обе половины ключа памяти всё равно берутся
вместе, просто из разных мест. Поля просятся прямо в ChannelInfo. Если аргумент
против - совместимость сериализованных сессий при откате релиза, это лечится
терпимой десериализацией по dataclasses.fields, а не новым типом.
