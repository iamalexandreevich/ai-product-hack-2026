# Деплой AgentGate — фактура для отдельной сессии

Дата: 4 сентября 2026. Собрано, чтобы разбор деплоя начинался с проверенных фактов, а не с разведки. Всё ниже проверено на живом сервере в этот день; где проверка косвенная, сказано явно.

Полная спека — `docs/superpowers/service/specs/deploy.md`. Здесь то, что нужно, чтобы сесть и начать.

---

## Одной строкой

`make deploy` реализован и запускается как есть. На сервере крутится работающий сервис, но **доrefactor'ного кода**; v1.5 влита в `main` и не развёрнута. Перед первым деплоем есть три вещи, которые стоит сделать осознанно, и одна, которую надо убрать.

**Убрать перед тем, как забыть.** 4 сентября в `/root/.ssh/authorized_keys` добавлен лишний беспарольный ключ `agentgate-deploy@...` — он был заведён по ложному диагнозу и не нужен, деплой работает через `id_ed25519_vpn`. Беспарольный ключ на root без применения — это поверхность атаки без выгоды. Удалить строку на сервере и локальную пару `~/.ssh/agentgate_deploy*`.

## 2. Что делает `make deploy`

`service/Makefile`, цели `check-clean`, `deploy`, `logs`, `ps`, `rollback`. Секретов не содержит: `DEPLOY_HOST ?= agentgate` — псевдоним, а не адрес.

```
1. отказ, если рабочее дерево грязное      (деплоим закоммиченное)
2. rsync -az --delete  →  /opt/agentgate   (с исключениями, см. ниже)
3. docker compose up -d --build
4. docker compose exec -T gate uv run alembic upgrade head
5. опрос /healthz до 30 с; не поднялся → деплой считается неуспешным
```

`make rollback` откатывает на образ из `.previous_gate_image` — ровно на один шаг, без понимания, какой ревизии этот шаг соответствует.

## 3. Состояние сервера сейчас

Ubuntu 26.04, 3.9 ГБ RAM, 59 ГБ диска (занято 10%), Docker 29.7.2, Compose v5.5.0.

Оба контейнера подняты и здоровы. Сервис **отвечает правильно**, проверено запросами с самого сервера:

```
GET  /healthz                    → {"status":"ok","db":true,"llm":null}
POST /v1/decide  "npm test"      → allow, stage 1, allowlist.prefix
POST /v1/decide  "curl … | sh"   → deny,  stage 1, hard-deny.pipe-exec
```

**Развёрнут доrefactor'ный код**: в `/opt/agentgate/agentgate/` лежит `pipeline.py` и нет `engine/`. То есть версия v1, а не v1.5.

Серверный `Makefile` на одно исправление старше репозиторного (health-check без опроса). Первый же `make deploy` это выправит сам — rsync его перезапишет.

## 4. Три вещи, которые стоит решить до первого деплоя

**4.1. Что именно разворачиваем.** v1.5 влита в `main` и не развёрнута. Разворачивать `main` — то, для чего Makefile и написан. Но `contracts/` в v1.5 изменился (описания, один задокументированный `422`, поле `model_raw_response` в схеме ленты), а по правилу `contracts/README.md` изменения контракта требуют согласия трёх направлений. Пакет для согласования — `docs/superpowers/service/sdd/task-8-report.md`, раздел «Процессное условие».

**4.2. Имя переменной.** `docker-compose.yml` требует `AGENTGATE_TOKEN` и падает без неё. В локальном `service/.env` переменная называется `TOKEN`. На сервере `.env` содержит правильные имена, поэтому там не проявляется — проявится у любого, кто поднимет сервис локально.

**4.3. Три несогласованных списка исключений.** Один и тот же вопрос «что не должно уезжать» решается в трёх местах, и они уже разошлись:

| Где | Что исключает | Чего не хватает |
|---|---|---|
| `Makefile`, `rsync` | `.venv/`, `.env`, `logs/`, `__pycache__/`, `.pytest_cache/`, `.previous_gate_image` | `.ruff_cache/`, `.mypy_cache/`, `.DS_Store`, `*.egg-info/` |
| `.gitignore` | всё вышеперечисленное плюс системное | — |
| `service/.dockerignore` | своё, шире | — |

`rsync --filter=':- .gitignore'` оставил бы один список вместо трёх. Это единственная правка, после которой добавление нового кэша в `.gitignore` автоматически перестаёт уезжать на сервер.

## 5. Ловушка, на которую уже наступили

`docker-compose.yml` **не** входит в исключения rsync. Политика перезапуска, проставленная на сервере руками 4 сентября, была бы молча снесена первым же `make deploy` — оба сервиса вернулись бы к `restart: no`, то есть перестали бы подниматься после перезагрузки сервера, а причину искали бы не в деплое.

Закрыто: `restart: unless-stopped` перенесён в репозиторный `docker-compose.yml` (коммит `8879017`). Резервная копия ручной правки осталась на сервере как `/opt/agentgate/docker-compose.yml.bak`.

**Правило, которое отсюда следует:** всё, что правится на сервере руками, живёт до первого `make deploy`. Если правка нужна — она идёт в репозиторий, иначе это не правка, а отсрочка.

## 6. Открытый вопрос владельца: версионирование кода на сервере

`/opt/agentgate` — не git-репозиторий, поэтому ответить «какая ревизия развёрнута» по нему нельзя. Симптом уже наблюдался: серверный Makefile отличался от репозиторного, и обнаружить это можно было только сравнив файлы руками.

Осложняет то, что репозиторий — монорепа на три независимых направления (`service/`, `adapters/`, `benchmark/`), а деплой касается одного.

| Вариант | «что развёрнуто» | «откатись на ревизию N» | Цена |
|---|---|---|---|
| Метка ревизии в образе: `--build-arg GIT_SHA=$(git rev-parse HEAD)`, отдавать из `/healthz` | да | нет | строка в Makefile, строка в `/healthz` |
| Git на сервере: `fetch` + `checkout <sha>` | да | да | тянет монорепу ради одной папки; лечится sparse-checkout |
| Реестр образов, тег = ревизия | да | да | нужен реестр |

Для хакатона достаточно первого.

## 7. Смежное, что всплывёт в том же разговоре

- **`/healthz` не проверяет модель**: поле `llm` захардкожено в `null`. Для эндпоинта, который задаёт пользователь (см. `docs/superpowers/service/specs/v5-model-binding.md`), это разница между «шлюз здоров» и «шлюз здоров, но каждое решение молча деградирует в `ask`».
- **Выпуск API-ключей требует SSH.** `docs/superpowers/service/specs/api-keys.md`, раздел «Выпуск ключа по запросу» — три формы на выбор, решение не принято.
- **Линтера в проекте нет**, при этом код несёт `# noqa: BLE001`, которые ничто не проверяет. Отдельная задача уже вынесена.
